# design-compare Skill（判断のための HTML を出して選んでもらう）

> **Core Principle**: 案や指摘は言葉で説明するより、**差が見える 1 枚の HTML に並べて判断してもらう**。
> 完璧な再現は不要 — 「この差でどれがいいか」を判断できる最小のモックでよい。
> 作り込みに時間をかけず、案出しの一部として素早く出す。

## いつ使うか

- デザイン・スタイルの変更案を 2 つ以上出すとき（ユーザーの明示依頼がなくても原則出す）
- README・スキルシート・設計メモなど Markdown 文書の**構成案**を 2 つ以上出すとき
- 公開文書の**文言案**を 2 つ以上出すとき。前後の行と並べて初めて重複や座りの悪さが見えるので、1 行の違いでも並べる価値がある
- 文書を通読して**指摘が多数出たとき**。チャットに列挙すると判断が追えなくなる
- **まとめて直した後**に、何がどう変わったかを確認してもらうとき
- 使わない場面: 案が 1 つしかないとき・ユーザーが文言を具体的に指示したとき・誤字や記法の明らかな修正

## 3 つの型

| | 比較型 | 選択票型 | 変更履歴ビュー |
|---|---|---|---|
| 使う場面 | 1 つの箇所に案が 2〜5 個 | 箇所が多数で、件ごとに判断が要る | まとめて適用した結果を確認してもらう |
| ユーザーの操作 | 案を 1 つ選ぶ | 件ごとに案を押す／編集欄を直す | 章ごとに読み、気になる行だけ「戻す」かコメント |
| 雛形 | `assets/markdown-compare.html` | `assets/review-picker.html` | `assets/redline.py` |
| 手順 | `references/compare.md` | `references/review.md` | `references/review.md` |

**判断の回数を最小にするのが設計の軸**。人が 1 件ずつ承認できるのは 30〜40 件が限度（実測）。それを超える指摘は「検証を通った分は先に当てて変更履歴ビューで確認 → 判断が要る分だけ選択票」の二段にする。詳細は `references/review.md`。

## どの型でも守ること

1. **置き場所は消えない場所**。`/tmp` 配下の scratchpad は数日で掃除されて消える。期間が空くレビューでは `~/.claude/projects/<project>/review-state/` のような永続する場所に、ページと生成データを置く
2. self-contained な単一 HTML・`lang="ja"`。外部 CDN・外部フォントは使わない
3. **実物の値を使う**。色・フォントサイズ・余白は対象実装から読み取った実値、表示テキストも実データ
4. **必ず「現状」を最初に置く**（差のベースライン）
5. 差分を色で示す。足す部分は緑の下線か黄色の背景、削る部分は赤の取り消し線。冒頭に凡例を 1 行書く
6. 案は**縦に並べる**。横並びのグリッドは幅が実寸にならない
7. 1 行に収まるかが論点になる文書では、各案の下に実測値を添える。**案を作る段階で毎回測らず、明らかに長い候補を落としてから、残りをまとめて 1 回で測る**
8. **ページを勝手に開き直さない**。`open` や SendUserFile で再描画すると、ユーザーが入力中のコメントや印が消える。開くのは最初の 1 回と、頼まれたときだけ。更新したら「更新した。開き直すときは今の入力を先に出してから」と伝える

## 提示の仕方

- 最初の 1 回は **`open` で開いてよい**（判断用ページは例外とするユーザー許可済み）。フルパスも提示する
- (Claude Code のみ) SendUserFile（display: render）でも送る。ただしこれも最初の 1 回だけ
- 見た目に出ない差（実装コスト・保守性など）はチャット側で補足する
- 推し案とその理由は、ページ内のバッジとチャットの両方に書く
- ユーザーが選んだら実装に進む。ページは使い捨てで、commit しない
