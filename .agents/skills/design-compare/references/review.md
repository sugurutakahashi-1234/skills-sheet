# 選択票型（指摘を一覧して、件ごとに方針を決めてもらう）

文書を通読して指摘が 5 件以上出たときに使う。雛形は `assets/review-picker.html`。
雛形の `CONFIG` と `ITEMS` だけ書き換えれば動く。HTML を組み立てる必要はない。

## 二段構えで進める

1. **一巡目（三択）**: 全件に「修正する / 要検討 / スキップ」を出す。各件に修正案を 1 つ添える
2. **二巡目（案モード）**: 一巡目で「要検討」が付いた件に、案を 3 つ出す

一巡目で案を 3 つずつ出すと、件数 × 案数で読む量が爆発する。まず 1 案で方針を決めてもらい、迷った件だけ広げる。

## 一件に必ず揃えるもの

- **場所**: 行番号 + どの節か（`203 行目 / No.10 経験した技術`）。行番号だけでは探せない
- **何が気になるか**: 1〜2 文。「読みにくい」で終わらせず、理由を書く（修飾のかかり先、語の重複、他の箇所との不統一）
- **現状**: その行そのまま。消す部分を `<d>…</d>` で囲む
- **修正後**: 足す部分を `<a>…</a>` で囲む。変わらない部分は同じ文字列を置く
- **実測値**: 1 行に収まるかが論点になる文書では `776px → 782px` のように現状と修正後の両方

指摘をグループに分けると判断が速くなる。誤記・表記の不統一／意味が取りにくい／日本語のねじれ／構成と言い方、の 4 つでだいたい収まる。グループごとに一括ボタンが出るので、「誤記は全部修正」のような処理ができる。

## 既定値は自分の推奨にする

`rec` に推奨を入れる（案モードでは先頭の案が既定）。全件ニュートラルにすると、ユーザーが 30 件すべてを押すことになる。推奨を入れておけば、変えたい件だけ押せば済む。

誤記や他の箇所との不統一は `fix`、言い方の強さや構成の話は `review` を既定にするとだいたい合う。

## 編集欄

案モードでは、案を押すとその案の文が編集欄に入る。ユーザーはそこを直接直せる。
これは「案A でいいけど 1 語だけ違う」という最も多いケースを、往復なしで拾うための仕掛け。

三択モードでは「ひとこと」欄として空で置く。書かれていれば結果に出る。

編集欄に何か書かれていたら、選ばれた案より**編集後の文を優先する**。ただし編集ミス（語の重複など）が混ざることがあるので、適用前に読んで、直したら何を直したか報告する。

## 案を分ける／行を増やすとき

1 行に 2 つの主張が入っている指摘では、「箇条書きを 2 行に分ける」案を出すことがある。
このとき**ページ上でも実際に 2 つの `li` として描く**。1 つの `li` の中で改行やダッシュで繋ぐと、ユーザーには別の表記に見えて拒否される。雛形の `text` は配列なので、要素を 2 つにすればよい。

## 結果の受け取り方

`file://` ではクリップボード API が使えないので、テキストエリアに出して「全選択」ボタンを添える。ユーザーはそれをコピーしてチャットに貼る。出力はこの形になる。

```
#1 [修正] 203 行目 / No.10 経験した技術
#11 案B 139 行目 / No.11 取り組み・貢献
    → 編集あり: 構造化は決定論的な変換に任せるなど、AI と機械的な処理の使い分けを徹底
#24 このまま 84 行目 / No.11 チーム体制

[全体へのコメント]
強みの節が長いので項目を絞りたい
```

## 適用するとき

- 「修正」と「案 + 編集文」を反映し、「スキップ」は触らない
- 置換は 1 箇所ずつ一意性を確かめる（同じ文字列が他にもあると事故になる）
- 適用後に幅の検査と lint を通し、副作用（修正で折り返しが増えた行）を確認する
- 1 コミットにまとめるか分けるかは件数で決める。20 件を超えるなら「誤記」「言い回し」で分けると履歴が読める
