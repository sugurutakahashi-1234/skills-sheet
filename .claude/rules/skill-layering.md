# スキル・ルールの置き場所と書き方

スキルやルールを新しく作るとき・大きく育てたときは、書き始める前に置き場所を判断する。知見は上の層へ集約するほど再利用され、リポジトリに死蔵するほど腐る。

## 4 層と判断基準

| 層 | 置き場所 | 判断基準 |
|---|---|---|
| 外部由来 | 消費側 `rulesync.jsonc` の `sources` に上流リポを直接書く。全リポで使うものはマシン設定リポジトリの skills CLI 台帳 | 他人の配布物。改変せず参照する。本文に手を入れるなら派生として汎用層で所有する |
| 汎用 | `sugurutakahashi-1234/ai-rules` | 会社名・ブランド・社内システムへの依存が本文に一切ない。他社業務でもそのまま使える |
| 会社固有 | 会社のルールリポ（例: `<org>/<org>-ai-rules`） | 会社のブランド・テーマ・製品・社内運用に依存する。ただし複数リポで使う |
| リポ固有 | そのリポの `.rulesync/skills/` / `.rulesync/rules/` | そのリポの構成・スクリプトに密結合。まずはここから始めてよい |

## 運用ルール

- 迷ったらリポ固有から始める。ただし作ったスキルに会社名依存が無いなら、最初から汎用層に書くことを検討する
- 同じスキルを 2 つめのリポにコピーしたくなった瞬間が昇格のサイン。コピーせず、上の層へ移して両方から `rulesync.jsonc` の `sources` で参照する
- 同じ層の中で新しいスキルを立てるかは、出力形式ではなく目的と発火条件で決める。目的が同じで発火条件も重なるなら、既存スキルに型を足す（`design-compare` が案の比較モックとレビューの選択票を 1 つに持つのがこれ）。名前を「視覚化」のような広い語にまとめると、どの場面で起動すべきかの判定が鈍る
- 昇格の手順: 上の層のリポへ本文と同梱ファイルを移して push → 各リポの `rulesync.jsonc` の `skills` 選定に追加してローカルコピーを削除 → `rulesync install --update && rulesync generate`。`--update` が要る（`install` 単体は lockfile に記録済みの ref で取得するため、push したばかりのスキルはその ref に存在せず、エラーにもならず黙って取得されない。上流が動いていない状態で選定を広げるだけなら `install` でよい）
- 汎用層に置くときは会社依存箇所（ブランド名・URL・テーマ・社内用語・顧客名を含むパス）を汎用化してから移す。汎用化できない部分は会社層に分離する
- 外部由来のスキルはコピーせず `sources` で参照する。本文に手を入れるときだけコピーし、派生として所有する: LICENSE を同梱し、frontmatter に `source` と `forked_at`（元にした commit）を残し、本文冒頭に由来を 1 行書く（生成ツールが frontmatter のメタデータを落とすことがあるため）。派生は上流に追従しない。上流との差と上位互換は `skills-review` で点検する
- AI エージェントは、ユーザーからスキル作成を依頼されたらどの層に置くかを判断して提案すること。汎用層・会社層に置く場合は該当リポジトリでの作業になる旨を伝える

## 共有スキル・ルールを変えるとき

消費側のリポジトリで、`sources` から取り込んだスキル・ルールを直したくなったときの扱い。生成物（`.claude/skills/` `.agents/skills/` `CLAUDE.md` など）を手で直しても次の `rulesync generate` で消え、同じものを使う他のリポジトリにも届かない。直すのは上流の正本になる。上流を直すと、それを選んでいる全リポジトリに次の更新で効く。

- 直す前に、その名前を選んでいるリポジトリを `ai-rules-update` の `usage` で逆引きする。ローカルに clone していないリポジトリは数に入らないので、件数は下限として扱う
- 利用リポジトリごとに、そのスキル・ルールがどう使われているか（CLAUDE.md・AGENTS.md・`.rulesync/rules/` での参照、選んでいる他のスキルとの組み合わせ）を読み、今回の変更が効くか・邪魔になるかを 1 行ずつ書いた表をユーザーに見せる。ユーザーは上流を直すつもりがなく、目の前のリポジトリだけを直したいと思っていることが多いので、影響の広さを先に見せる
- 判定は 3 つから出す。全員に効く改善なら上流を直す。目的と発火条件が同じで出力の型だけが違うなら、同じスキルに型を足す。目的か発火条件が違うなら別のスキルに分ける（そのリポジトリだけの事情ならリポ固有層に置く）
- 承認されたら上流を直して push する。利用リポジトリへは今すぐ配らない。各リポジトリは次にそこで作業するとき、セッション開始の遅れの知らせ（`rulesync-freshness`）を見て、その場で上げるかを決める。一括で配り直す（`ai-rules-update`）のは、ユーザーが頼んだときと、利用側で壊れている不具合を直したときだけ。全リポジトリを毎回上げると、変更のたびに取得・生成・検証とコミットが利用リポジトリの数だけ走り、手間とトークンがかかる
- 外部由来のスキルは上流を直せない。手を入れるなら派生として所有するか、消費側のリポ固有スキルで補う

## 書き方

今のモデル（Claude Opus 5.5 / Fable 5.1、GPT-6 Astra）は指示への感度が高く、目的を伝えれば段取りは自分で組む。前の世代向けに書いた足場はそのまま残すと逆効果になる。Anthropic も OpenAI も「前モデル向けのスキルは今のモデルには手順が細かすぎ、出力を悪化させうる」として棚卸しを勧めている。

- **理由を書く。** 「X するな」だけより「Y が起きるので X しない」の方が守られ、書いていない類似ケースにも一般化される
- **強調語を使わない。** `CRITICAL` / `MUST` / 全部大文字 / 「必ず」「絶対」の連打は、感度の高いモデルでは過剰反応（頼んでいない場面での発火・過剰な検証）を生み、多用すると何も目立たなくなる。普通の文で「〜のときは〜する」と書く。どうしても 1 行だけ守られないときにその 1 行にだけ印を付ける
- **禁止形より肯定形。** 「Markdown を使うな」より「流れる散文で書く」の方が狙った出力になる
- **ハーネスとモデルが既に持つ振る舞いを重ねない。** 「自分の仕事を検証しろ」「テストを回せ」「二重に確認しろ」「進捗を報告しろ」は Claude Code / Codex のシステムプロンプトとモデル自身が持っている。重ねると過剰検証でトークンと時間が増えるだけで品質は上がらない。書くのは「どこまで検証すれば足りるか」「どの状況では止まって聞くか」といった境界の側
- **「作業前に A と B と C を全部読め」と書かない。** 「サービス境界は A、スキーマ変更は B を見る」のように、いつ何を見るかで書く。前者は毎回のツール呼び出しを増やし、後者は必要なときだけ読まれる
- **矛盾を残さない。** ルール・スキル・AGENTS.md の間で指示が食い違うと、モデルは止まる・別方向へ動く・ユーザーの意図しない方の指示に従う、のどれかになる。優先順位を明示し、古い指示は消す。GPT-6 Astra は特にこの影響が出やすい
- **存在しないスキル・ファイルを参照しない。** 別リポ固有のスキル名やパスを汎用層の本文に残さない
- **description は短く、発火条件を具体的に。** Claude Code は description で自動起動を決め、Codex は多数導入時に description を切り詰めて表示するので、主要な用途と引き金になる語を先頭に置く。「データベースを触るとき」ではなく「マイグレーションを足す・変えるとき」。第三者視点の命令形で書く
- **同梱スクリプトは単体で使い方が分かるようにする。** `--help` で使い方を標準出力に出して終了 0、引数が合わないときは使い方を標準エラーに出して 0 以外で終える。結果は標準出力、途中経過は標準エラーに分ける（結果を JSON で返す約束のスクリプトは、エラーも JSON で返してよい）。ファイルや外部の状態を書き換える操作は、明示の引数（`--apply` など）を付けたときだけ行う。SKILL.md の説明とスクリプトがずれたとき、呼んだ側がその場で気づけるようにするため
- **本文は 500 行以内。** 判断材料・落とし穴・環境固有の癖を本文に置き、長い参考資料・雛形・スクリプトは `references/` `scripts/` `assets/` に分けて本文から指す（progressive disclosure）
- **常時読まれる量を意識する。** `globs` の無いルールはセッション開始時に全部読まれる。Claude Code は CLAUDE.md を 200 行目安、Codex は AGENTS.md の合計を既定 32 KiB で打ち切る。ファイル作業時だけ効けばよいルールには `globs` を書く
- **確実に止めたい線は指示ではなく設定に置く。** ルールは文脈であって強制ではない。Claude Code なら `permissions.deny` と `PreToolUse` hook、CI なら `needs` と検査ジョブ。指示には「なぜその線があるか」だけを残す
- **書いたら外して比べる。** スキルを外して同じ依頼を素のモデルに投げ、差が出ない部分は消す。モデルが更新されたら `skills-review` で同じ点検をやり直す

## 教訓の反映（フィードバックをスキルへ継ぎ足す）

作業中に得た教訓・ユーザーからのフィードバックは、行動が変わるべきスキル/ルールの該当セクションへ直接反映する。別ファイルの lessons メモはエージェントに読まれず腐る。

- 本文は「現在の正」を上書きする形で書き、時系列ログにしない。経緯は git と issue が持っている
- 日付を書き添えるのは「日付自体に意味がある教訓」だけ（課金方針・外部仕様など、時間経過で前提が変わりうるもの）
- 反映先の層は上の 4 層判断と同じ: 汎用の教訓 → 汎用層のスキルを直して push / 会社固有 → 会社層 / そのリポだけ → そのリポの main.md かローカルスキル。汎用層・会社層を直すときは「共有スキル・ルールを変えるとき」の影響確認を通す
- Claude Code の auto memory はマシンローカルで、他の人にも他のマシンにも共有されない。個人の作業の癖や進行中の文脈はそこに置いてよいが、他の人や別環境でも効くべき教訓はスキル/ルールに書く
- AI エージェントは、ユーザーのフィードバックが再利用可能な教訓だと判断したら「この教訓を○層の△スキルへ反映しますか？」と提案すること（勝手にコミットはしない）

## 何をスキル・ハーネスとして残すか

モデルの進歩で、スキルやハーネスの多くは不要になっている。残す価値があるかは「手順を教えているか、境界を引いているか」で判断する（2026-09 時点の判断。モデルが進むほど手順型の価値は下がり続ける）。

- **残す: 外側のガードレール型。** モデルが自力では守れない制約や、守らせたい行動の境界を引くもの。破壊的操作の禁止、コミット規約、ブランドの確定ルール、「作る前に問い詰める」（grill-me 系）、環境固有のツールの癖（課金経路・CLI の落とし穴・特定 CLI の引数の罠）など。モデルが賢くなっても消えない
- **消す: 手順を一つずつ与える型。** 「まず A を読み、次に B を作り、C を検査する」のような段取りの指示。今のモデルは目的を伝えれば自分で段取りできるので、手順型スキルはコンテキストを食うだけになりやすい。手順の中に上の「消えない知識」が混ざっているなら、その部分だけを短く残して手順は捨てる
- グローバル（全セッションで description が読まれる）に置くのはガードレール型だけにする。手順型・成果物の型（比較モック、PDF 変換、図の書き出しなど）は、それを使うリポジトリの sources に入れる
