# スキルシートの言い回し

README を直すたびに決まった判断を残す。新しく決めたことはこのファイルに追記する。

## 文末

- 見出しも箇条書きも名詞で止める。`〜力` `〜を担当` `〜を経験` `〜の経験` はいずれも体言止めとして使ってよい
- 同じ文末を 3 行以上続けない。1 つの節で `担当` で終わる行は 2 行までを目安に、`設計` `導入` `推進` `確立` `実装` などで散らす
- 動詞で終わる行（`作る` `実装できる`）と名詞で終わる行を混ぜない。`実装できる` のような自己申告は実績の言い方（`実案件で実装`）に変える
- 動詞を名詞で包んだ言い方は縮める（`構成を選ぶ判断` → `構成の選定`）
- 同じ行に同じ語を 2 回入れない（`実装担当者まで…相談・提案を担当`）

## 強さの出し方

- 形容詞や自称ではなく、固有名詞と数値で示す。`モダン` と書く代わりに `Bun・Hono・oRPC・Drizzle・TanStack Start` を並べ、`トップクラス` と書く代わりに件数と規模を書く
- 誰でも書ける文は技術名に置き換える（`フロントエンドからサーバーサイドまで実装できる` → 使っている技術を並べる）
- `エキスパート` のような自己申告の肩書きは、裏づけの行が同じなら書かない方が強く見える
- 説明を求められて答えられない専門用語は載せない（`Schema.org` `Content-Signal` を落とした判断がこれ）

## 見出し

- 見出しの深さは 3 段で固定する。`##` は大節（基本情報 / 強み / 職務経歴 / 案件詳細 / 技術スタック。技術スタックは照合用の索引なので巻末に置く。見出しは `## 1. 基本情報` `### 5.1 AI` のように番号付きで、番号は pre-commit が振る。案件の `[No.N]` には振らない）、`###` はその中のグループ（技術分野・所属・`[No.N]` の案件）、`####` は案件内の定型 6 節（期間 / チーム体制 / 案件概要・担当業務 / 経験した技術 / 取り組み・貢献 / 開発環境）。`#####` は使わない
- それより細かい区分は見出しにせず、`- **項目**` の太字と子の箇条書きで書く（技術スタックの `- **クラウド**` → `- **Cloudflare**` → 細目、と同じ形。3 段までの入れ子を許容）。Web 版はこの規則を前提に、h4 をカードの見出し・太字項目をカード内の小見出しとして描く
- 案件詳細の見出しは `### [No.N] 案件名（客先）` で、職務経歴の一覧行の 1 行目と同じ文字列にする（リンク記法だけは見出しに書かない）。役割・技術は一覧行の子行 `**役割**（技術）: 概要` に書き、見出しに重ねない。Web 版はこの一致を前提に一覧行と詳細を合体させ、ビルドで検証する
- 実績の件数を名乗る見出しは、根拠が 1 案件しかないなら視点の主張に言い換える（`KPI 起点のグロース施策` → `ビジネス KPI 起点での開発経験`）
- 括弧の補足は、子の箇条書きと重複するなら外す（`FDE（AI 活用の相談・提案〜実装・導入）` → `FDE としての AI 活用支援`）
- 1 つの項目に子行が 1 行しかない状態を作らない。2〜3 行に揃えるか、他の項目にまとめる

## 語の選び方

- 総称でぼかさず、案件詳細で使っている語に合わせる。強みの `社内 IT` を `社内インフラ` に直したのがこれ（案件詳細では `社内インフラ管理` と書いている）
- 1 行に主張を 2 つ入れない。読点で別の仕組みをつなぐと、どちらの印象も薄くなる（`採用応募対応を自動化、Access 認証付きの資料配信` を分けたのがこれ）

## 技術名のバッククォート

- 技術スタックの細目・案件の開発環境・職務経歴の一覧行の技術部分では、製品名・ライブラリ名をバッククォートで囲む（`` `React` ``）。Web 版はこの 3 か所の `code` をタグ（チップ）にし、隣り合うタグの間の `, ` `・` は表示しない
- 囲むのは名前だけ。全体にかかる注記は行末に括弧で書く（`` LLM: `GLM`, `Kimi`（Cloudflare AI Gateway 経由） ``）。1 つにかかる補足は名前の中に入れる（`` `SQLite (Cloudflare D1)` `` `` `Swift (SwiftUI, UIKit)` ``）
- 文の中の名前は囲まなくてよい。囲んだ場合も上の 3 か所以外では Web 版は普通のインラインコード表示になる（No.9 の経験した技術の `` `Riverpod` と `Hooks` を用いた状態管理 `` はこれ）
- 開発環境は名前だけの一覧にする。文で書きたい内容（アーキテクチャの構成など）は「経験した技術」か「取り組み・貢献」に書く

## 2026-10-02 の強みの組み直しで決めたこと

- 強みの読み手は CTO・リードを探す企業。項目は経歴の分類（CTO / AI / FDE / 0 → 1 / …）を並べるのではなく、何ができるかの軸で立てる。分類を並べると目次のように読め、「いろいろやっている人」という印象で止まる
- 強みは技術名と担当範囲で書く。MCP のツール数・GitHub のスター数・記事数のような小さい数字や、1 件だけの事例は、強みに出すとかえって弱く見えるので案件詳細に置く
- 開発環境や技術スタックと名前が重なることは、文を削る理由にしない。削るかどうかは、行そのものが弱いか（どのチームでもやる運用、成果が書けない、同じ主張の 2 回目）で決める
- 技術スタックの 1 行には同じ種類のものだけを並べる。種類の違うものを `RAG / 検索` のような括りでまとめない（ベクトル DB と推論基盤は別の行）。ラベルと中身が対応している `リリース / デプロイ` はそのままでよい。Linter と Formatter は役割が別なので `Linter:` `Formatter:` の 2 行に分ける（両方を担う `Biome` は両方に入れる）
- 見れば分かるラベル（`言語:`）は付けない。サーバーサイドの言語・ランタイム・フレームワークは `実装:` の 1 行に並べる

## 2026-10-04 の職務経歴の一覧行で決めたこと

- 一覧行の子行は `**役割**（`言語`・`特徴`）: 概要` の 1 行にする。`役割 / 技術 / 概要` のスラッシュ区切りは、案件名（`IT コンサルティング / SIer / SES`）の中のスラッシュと紛れて区切りが読めないのでやめた。Web 版（build-site）はこの形を前提に役割・技術・概要へ分け、崩れていたらビルドを止める
- 技術は全部を並べず、「言語 1 つ + 案件を特徴づけるもの」を 2〜4 個（No.8 は `Swift`・`WhisperKit`、No.11 は `Cloudflare`・`RAG`・`MCP`）。`FDE` のような技術でない語は括弧に入れない。技術の全体は案件詳細の開発環境と技術スタックにある
- 一覧行では言語を `Swift` `PHP` と括弧なしで書く。`Swift (SwiftUI)` を括弧の中に入れると二重括弧になり読みにくい。技術スタック・開発環境の `Swift (SwiftUI, UIKit)` のような書き方はそのまま
- 幅はコード（バッククォート）込みで測る。等幅の字体で左右に余白が付くので、普通の文字として数えると狭く見積もる（この見落としで、旧形式の 4 行が GitHub で折り返していた）
