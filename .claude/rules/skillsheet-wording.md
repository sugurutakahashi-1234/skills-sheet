# スキルシートの言い回し

README を直すときの決め。文そのものは README が持ち、経緯は git が持つので、ここには型と理由だけを書く。新しい決めは該当する節に足し、古い決めと矛盾したら古い方を消す。表記の統一は prh.yml にも足して機械で止める。

## 読み手と打ち出し

- 強みの読み手は CTO・リードを探す企業。項目は経歴の分類（CTO / AI / FDE / 0 → 1 …）ではなく、何ができるかの軸で立てる。分類を並べると目次のように読め、「いろいろやっている人」という印象で止まる
- 強みは技術名と担当範囲で書く。小さい数字（MCP のツール数・GitHub のスター数・記事数）、1 件だけの事例、具体すぎる期間（「1 週間で回し」）は案件詳細に置く
- 強みの「フルスタックの実装力」は項目を分けず、行の頭に `フロントエンド / モバイル:` `サーバーサイド:` `インフラ:` のラベルを付ける
- AI の実績は「AI を組み込んだ」ではなく、何を何に任せたかを書く。打ち出しは、コストを見据えて LLM に任せる処理を絞った設計（一次判定を分類モデル（Jev）に任せる）
- 数字は、本番での実績か過去データでの評価かを書き分ける。評価で決めた値は「除外」「閾値を決めて導入」と書き、「削減した」とは書かない。根拠のない数字は書かない。比率は「約 1/3 削減」のように向きを書く（「1/3 に」は 3 分の 1 になったと読める）
- 担当範囲は「設計から実装、運用までを担当」と工程を並べて書く

## 文末

- 見出しも箇条書きも名詞で止める。`〜力` `〜を担当` `〜を経験` `〜の経験` はいずれも体言止めとして使ってよい
- 同じ文末を 3 行以上続けない。1 つの節で `担当` で終わる行は 2 行までを目安に、`設計` `導入` `推進` `確立` `実装` などで散らす。「〜した経験」にも揃えない
- `検証` `抑制` のような動作の名詞で止まると、途中で終わったように聞こえる。締めの語を足す（`A/B テストで効果を検証する改善サイクルの運用`）
- 動詞で終わる行（`作る` `実装できる`）と名詞で終わる行を混ぜない。`実装できる` のような自己申告は実績の言い方（`実案件で実装`）に変える
- 動詞を名詞で包んだ言い方は縮める（`構成を選ぶ判断` → `構成の選定`）。同じ行に同じ語を 2 回入れない（`実装担当者まで…相談・提案を担当`）

## 読点

AI が書いた文に出やすい読点の型。文の切れ目にない読点は外し、2 つの動作の切れ目（`〜を逆算し、企画から実装まで担当`）と並列の列挙（`見積もり、実装、レビュー`）に打つ読点は残す。

- 1 つの名詞に修飾を 2 つ重ねて読点でつながない。修飾を 1 本にするか、動作を 2 つに分ける（`〜を絞る、コストを見据えた設計` → `LLM のコストを見据えて一次判定を分類モデル（Jev）に任せる設計`）
- 前置きの後に読点を打たない（`CTO として、〜を担当` → `CTO として〜を担当`。`〜アプリで、` `〜から、` `〜まで、` も同じ）
- 読点 2 つで 1 行を 3 つに刻まない。語を削って読点 1 つ以内にする（`FDE として、〜まで、〜を経験` → `FDE として〜まで支援`）
- 「〜で、」の前置きの後に同じ「で」を重ねない。目的語を先に出して前置きをやめる（`ブログで、〜をスライドで発信` → `〜の知見を Zenn と技術ブログで発信`）

## 強さの出し方

- 形容詞や自称ではなく、固有名詞と数値で示す。`モダン` と書く代わりに `Bun・Hono・oRPC・Drizzle・TanStack Start` を並べ、`トップクラス` と書く代わりに件数と規模を書く
- 誰でも書ける文は技術名に置き換える（`フロントエンドからサーバーサイドまで実装できる` → 使っている技術を並べる）
- `エキスパート` のような自己申告の肩書きは書かず、裏づけの行だけを残す
- 説明を求められて答えられない専門用語は載せない（`Schema.org` `Content-Signal` を落とした判断がこれ）
- 1 行に主張を 2 つ入れない。読点で別の仕組みをつなぐと、どちらの印象も薄くなる（`採用応募対応を自動化、Access 認証付きの資料配信` を分けたのがこれ）
- 行を削る基準は、行そのものの弱さ（同じ主張の 2 回目、どのチームでもやる運用で何が良くなったかが書けていない）。開発環境・技術スタックの名前と重なることや、ライブラリと用途を並べた行（`` `go_router` を用いた画面遷移の実装 ``）であることは、削る理由にしない

## 語の選び方

- 総称でぼかさず、案件詳細で使っている語に合わせる（強みの `社内 IT` → `社内インフラ`。案件詳細では `社内インフラ管理`）
- 役職名は英語で書く（`CTO` `PdM` `PM` `Scrum Master`）。「スクラムボード」「スクラムイベント」のような一般名詞はカタカナでよい
- Claude Code / Codex の機能は `Skills` と英語で書く。「スキル」だと技能の意味と混ざる（この文書はスキルシートなので特に）
- 製品名は正式名で書く。`Cloudflare Workflows` のように Cloudflare を付け、「（いずれも Cloudflare）」のような注記でまとめない。分類モデルは一般名に製品名を添えて「分類モデル（Jev）」（技術スタックの細目は `TypeSafe Jev`）
- 略語に揃える語: `DB`（項目名も `DB`。`RDBMS` のような定着した語はそのまま）、`CAC`・`LTV`（「獲得コスト」と書かない）
- AI 側は「判定」、人間側は「判断」で使い分ける（`AI の判定と人間の判断`）。処理を担うものを並べるときは「人」ではなく「人の判断」
- LLM の評価の仕組みは「評価スクリプト」「評価ハーネス」と書き、`eval` とは書かない（`eval` は同じ入力の組を各モデルに通して採点する仕組みを指す）
- `PDCA` は使わず、何を回したかを書く（「施策立案からリリースまでを 1 週間で回し」）
- 「工程」は要件定義のような開発工程と読まれるので、処理の段階を指すときは使わない（`処理ごとに`）
- 「LLM は精査に限定」「処理ごとの使い分け」のように、何をしたかが見えない言い方をしない。何を何に任せたか、数字は何の効果かを書く

## 見出しと構造

- 見出しの深さは 3 段で固定する。`##` は大節（基本情報 / 強み / 職務経歴 / 案件詳細 / 技術スタック。技術スタックは照合用の索引なので巻末に置く。番号は pre-commit が振り、案件の `[No.N]` には振らない）、`###` はその中のグループ（技術分野・所属・`[No.N]` の案件）、`####` は案件内の定型 6 節（期間 / チーム体制 / 案件概要・担当業務 / 経験した技術 / 取り組み・貢献 / 開発環境）。`#####` は使わない
- それより細かい区分は見出しにせず、`- **項目**` の太字と子の箇条書きで書く（技術スタックの `- **クラウド**` → `- **Cloudflare**` → 細目、と同じ形。3 段までの入れ子を許容）。Web 版はこの規則を前提に、h4 をカードの見出し・太字項目をカード内の小見出しとして描く
- 案件詳細の見出しは `### [No.N] 案件名（客先）` で、職務経歴の一覧行の 1 行目と同じ文字列にする（リンク記法だけは見出しに書かない）。役割・技術は一覧行の子行に書き、見出しに重ねない。Web 版はこの一致を前提に一覧行と詳細を合体させ、ビルドで検証する
- 見出しは件数ではなく視点で立てる（`KPI 起点のグロース施策` → `ビジネス KPI 起点での開発経験`）
- 括弧の補足は、子の箇条書きと重複するなら外す（`FDE（AI 活用の相談・提案〜実装・導入）` → `FDE としての AI 活用支援`）
- 1 つの項目に子行が 1 行しかない状態を作らない。2〜3 行に揃えるか、他の項目にまとめる
- 氏名は基本情報の先頭に `高橋 俊` と載せる（本人判断）。Web 版では氏名をプロフィールの一番上に大きく出す
- 案件ごとの期間は、案件詳細の最初の節 `#### 期間` に `- 2024年12月〜2025年5月` の 1 行で置く。案件名や summary には入れない（GitHub の Outline と案件一覧が長くなる）
- 技術スタックの 1 行には同じ種類のものだけを並べる。種類の違うものを `RAG / 検索` のような括りでまとめない（ベクトル DB と推論基盤は別の行）。Linter と Formatter は役割が別なので `Linter:` `Formatter:` の 2 行に分ける（両方を担う `Biome` は両方に入れる）。見れば分かるラベル（`言語:`）は付けず、サーバーサイドの言語・ランタイム・フレームワークは `実装:` の 1 行に並べる
- 開発環境は名前だけの一覧にする。文で書きたい内容（アーキテクチャの構成など）は「経験した技術」か「取り組み・貢献」に書く。エディタ単独の行は置かず、`Xcode` `Android Studio` `VSCode` は他のツールと同じ行に並べる。ツールの一覧は何を強制・検出しているかがラベルで分かる形にする（`未使用コード検出 / 依存関係ルールの強制`）

## 技術名のバッククォート

- 技術スタックの細目・案件の開発環境・職務経歴の一覧行の技術部分では、製品名・ライブラリ名をバッククォートで囲む（`` `React` ``）。Web 版はこの 3 か所の `code` をタグ（チップ）にし、隣り合うタグの間の `, ` `・` は表示しない
- 囲むのは名前だけ。全体にかかる注記は行末に括弧で書く（`` LLM: `GLM`, `Kimi`（Cloudflare AI Gateway 経由） ``）。1 つにかかる補足は名前の中に入れる（`` `SQLite (Cloudflare D1)` `` `` `Swift (SwiftUI, UIKit)` ``）
- 文の中の名前は囲まなくてよい。囲んだ場合も上の 3 か所以外では Web 版は普通のインラインコード表示になる（No.9 の経験した技術の `` `Riverpod` と `Hooks` を用いた状態管理 `` はこれ）

## 職務経歴の一覧行

- 一覧行の子行は `**役割**（`言語`・`特徴`）: 概要` の 1 行にする。`役割 / 技術 / 概要` のスラッシュ区切りは、案件名（`IT コンサルティング / SIer / SES`）の中のスラッシュと紛れて区切りが読めない。Web 版（build-site）はこの形を前提に役割・技術・概要へ分け、崩れていたらビルドを止める
- 技術は全部を並べず、「言語 1 つ + 案件を特徴づけるもの」を 2〜4 個（No.8 は `Swift`・`WhisperKit`、No.11 は `Cloudflare`・`RAG`・`MCP`）。`FDE` のような技術でない語は括弧に入れない。技術の全体は案件詳細の開発環境と技術スタックにある
- 一覧行では言語を `Swift` `PHP` と括弧なしで書く。`Swift (SwiftUI)` を括弧の中に入れると二重括弧になり読みにくい。技術スタック・開発環境の `Swift (SwiftUI, UIKit)` のような書き方はそのまま
