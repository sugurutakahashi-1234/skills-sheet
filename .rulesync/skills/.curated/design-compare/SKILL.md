# design-compare Skill（判断のための HTML を出して選んでもらう）

> **Core Principle**: 案や指摘は言葉で説明するより、**差が見える 1 枚の HTML に並べて選んでもらう**。
> 完璧な再現は不要 — 「この差でどれがいいか」を判断できる最小のモックでよい。
> 作り込みに時間をかけず、案出しの一部として素早く出す。

## いつ使うか

- デザイン・スタイルの変更案を 2 つ以上出すとき（ユーザーの明示依頼がなくても原則出す）
- README・スキルシート・設計メモなど Markdown 文書の**構成案**を 2 つ以上出すとき（セクションの分け方・見出し名・どこに何を書くか）
- 公開文書の**文言案**を 2 つ以上出すとき（見出しの言い回し、1 行の書き換え、括弧の補足の有無）。前後の行と並べて初めて重複や座りの悪さが見えるので、1 行の違いでも並べる価値がある
- 文書を通読して**指摘が多数出たとき**（誤記・表記の不統一・読みにくい言い回しなど）。チャットに列挙すると判断が追えなくなる
- 使わない場面: 案が 1 つしかないとき・ユーザーが文言を具体的に指示したとき・誤字や記法の明らかな修正

## 2 つの型

| | 比較型 | 選択票型 |
| --- | --- | --- |
| 使う場面 | 1 つの箇所に案が 2〜5 個ある | 箇所が 5 個以上あり、件ごとに方針を決める |
| ユーザーの操作 | 案を 1 つ選ぶ | 件ごとにボタンを押し、結果のテキストを返す |
| 雛形 | `assets/markdown-compare.html` | `assets/review-picker.html` |
| 手順 | `references/compare.md` | `references/review.md` |

迷ったら件数で決める。1 箇所について深く選ばせたいなら比較型、多くの箇所をさばくなら選択票型。
選択票型で「要検討」が付いた箇所に案を 3 つ出す、という二段構えもよく使う（この場合も雛形は選択票型のまま）。

## どちらの型でも守ること

1. **置き場所はセッションの scratchpad**。公開物ではないのでリポジトリ内に置かない（scratchpad が無い実行環境でだけ `.tmp/design-compare/` を使う）。
   ファイル名は `design-compare-<topic>.html` / `review-<topic>.html`
2. self-contained な単一 HTML・`lang="ja"`。外部 CDN・外部フォントは使わない
3. **実物の値を使う**。色・フォントサイズ・余白は対象実装から読み取った実値を使い、
   表示テキストも実ページの実データを使う（ダミー文字は折り返しや密度の判断を誤らせる）
4. **必ず「現状」を最初に置く**（差のベースライン。現状タグはグレーで区別）
5. 差分を色で示す。足す部分は黄色の背景、削る部分は赤の取り消し線。冒頭に凡例を 1 行書く
6. その論点では動かさない行はグレー（`.fixed`）にして、固定であることを示す
7. 案は**縦に並べる**。横並びのグリッドは幅が実寸にならず、折り返し・密度の差が見えなくなる
8. 1 行に収まるかどうかが論点になる文書（スキルシートなど）では、各案の下に実測値を添える。
   **案を作る段階で毎回測らず、明らかに長い候補を落としてから、残った案をまとめて 1 回で測る**
9. ブラウザ依存の CSS（`word-break: auto-phrase` など）を使う案には、対応状況をバッジで明記する

## 提示の仕方

- ページは **`open` で開いてよい**（他の成果物は「パス提示のみ」が原則だが、判断用ページは例外とするユーザー許可済み）。あわせてフルパスも提示する
- (Claude Code のみ) SendUserFile（display: render）でも送り、サイドパネルでも見られるようにする
- 見た目に出ない差（実装コスト・保守性・レスポンシブ対応への影響など）はチャット側の説明で補足する
- 推し案とその理由は、ページ内のバッジとチャットの両方に書く
- ユーザーが選んだら実装に進む。ページは使い捨てで、commit しない
