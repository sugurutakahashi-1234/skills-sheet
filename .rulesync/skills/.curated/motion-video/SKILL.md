# motion-video（モーショングラフィックス動画を本人と一緒に作る）

動画は HyperFrames（HTML と GSAP で組み、ブラウザで 1 フレームずつ撮って MP4 にする）で作る。組み立て・検査・書き出しの仕組みは HyperFrames の公式スキル（`hyperframes` `hyperframes-core` `media-use` など）が持っているので、ここでは重ねない。このスキルが担うのは、本人と方向を決めて仕上げるまでの進め方と、そこで使う道具。

題材ごとの決め（事実の出どころ・本人の好み・作業場所）は、使う側のリポジトリのスキルかルールに書く。ここには、どの題材でも効く話だけを置く。

## 前提

- 使う側のリポジトリが `heygen-com/hyperframes` のスキルを `sources` で取っている（選ぶ名前と取り込みの注意は ai-rules の README「よく使う外部 source」）
- `npx hyperframes` は Node 22 以上・Chrome・ffmpeg を使う。仮アニメーションの撮影（`capture-mock.ts`）は puppeteer、拍の測定（`beat-grid.py`）は uv、場面の並びの検査・見本の撮影（`check-scenes.ts` `sample.ts` `scene-windows.ts`）は Bun を使う
- 題材（事実の出どころ）・作業ディレクトリ・書き出した動画の置き場所を、使う側が決めている。決まっていなければ最初に聞く

## 進め方

序盤・中盤・終盤で、作る物と決めることが違う。序盤は広げて好みと話の筋を見つけ、中盤は通しの下書きで方向と中身を決め、終盤は見た目と動きを詰める。

序盤のテイストの見本は好みの方向を見つけるのに向き、話の筋は本人に語ってもらうと決まる。部品（配色・場面の絵）を選び重ねて全体まで決めようとすると、まとまりが出ずに決まらない。全体の方向は、通しの動画を方向違いで並べて選ぶ。方向が決まった後の直しは、見本で選んでから本番に入れると外れない。

### 序盤: 広げて、好みと筋を見つける

決まっていないものに合わせて、手段を使い分ける。1 つに絞らない。

- **テイストの見本**: 見た目の好みが言葉にならないとき。2 場面ほどを、方向を散らして 8〜9 通り、並列のエージェントに静止画か数秒の動きで描かせ、1 枚の選択票に並べる。散らし方は `references/concepts.md` の棚と `scripts/draw.ts`（互いに遠い組み合わせを引いて 1 体ずつに渡す）。ここで選ぶのはテイスト（密度・色・質感・動きの性格）で、全体の構成は決めない
- **ストーリーを聞く・出す**: 何をどの順で伝えるかが決まっていないとき。本人に、人に話すつもりで題材を語ってもらい、その言葉から筋の形（積み上がる・合流する・旅する など 1 語）と場面ごとの見出し 1 行を起こして返す。語りにくそうなら、筋の案を 3〜4 本、場面の見出しの並びとして文章で出して選んでもらう。見立て（積み木・地層）は筋の形と同じ形のものを選ぶ。筋が決まらないまま絵を選ぶと、「この数字は要らない」のような中身の不満が見た目の判断に混ざる
- **参考をもらう**: 本人が「こういうのがいい」と思う動画や画像を 2〜3 本もらい、何が良いのか（密度・動き・文字・色）を言葉にする

### 中盤: 通しの下書きで、方向と中身を決める

- テイストと筋がそろったら、最上位のモデルの作り手を 2〜3 体並列に立て、方向違いの通しの下書きを 1 本ずつ作らせて見比べてもらう。部品の静止画では「格好いいか」を判断できないが、通しで見られれば、見た目は本気・動きはカット割りと最小限・30 fps の軽い下書きで足りる。指示書には目標・中身・守る線・質の基準だけを書き、構図・動き・転換・密度は任せて大胆さを求める（場面ごとに置く要素まで決めると、誰が描いても平均的な絵になる）
- 選ばれた 1 本の上で、項目の足し引き・場面の順・尺を動かす。中身の議論（「この項目は要るか」「案件の話が無いと分からない」）はこの段階で必ず起きる。最初の下書きから、場面の並びと長さを JSON に持ち、場面ごとにファイルを分けた作りにしておく（下の「ループを速く回す」）と、場面の追加や並べ替えが JSON の書き換えで済む

### 終盤: 詰める

選ばれた 1 本を、仕上げの直しのループ（次の節）で磨く。詰める途中で方向のやり直しが出たら、序盤・中盤の手段に戻ってよい。

1 つの作品を場面ごとに別のエージェントに分けない（作りがそろわず、余白と主役が崩れる）。分けてよいのは、序盤のテイストの見本、方向違いの下書きを並列で作るとき、調べ物・測定・点検。

## 仕上げの直しのループ

本人が動画を見て出す直しを、1 回ずつ次の順で回す。軸は「作る前に、必ず画面で見せる」。動画は往復 1 回が重い（作り手の直し 1 回は数分〜20 分・数十万トークン）。画面で見せて確かめる往復は数十秒で済み、外れた作り直しを丸ごと減らせる。直し方の言葉が 1 通りに見えても（「分野を囲むか隙間を開ける」）、確かめずに作ると作り直しになりやすい。

1. **言葉を 2 つに分ける**: 「選んでもらうもの」（「どう見せるのがいいか」「囲うか隙間か」のように、言葉に 2 つ以上の形がありうるもの）と「そのまま直すもの」（消す・URL や文言を変える・尺を変える のように形が 1 つに決まるもの）
2. **選んでもらうものは、案を見せる**: まとめ役が見本を 3〜4 案作り、今の版の同じ場面も並べて選択票に出す。見本はできるだけ本番のコードの上に、JSON の値か URL のクエリで切り替わる形で作る（`scripts/sample.ts <作品> <名前> --patch '<JSON>' --at <時刻>` が、値を差し替えた写しで静止画か短い動画を撮る）。選ばれたら切り替えを既定にするだけで済む。本番と別に書いた見本は、選ばれた後に作り手が本番で組み直すことになり、往復の時間の多くを占める。本番に土台の無い新しい見せ方だけ、別の HTML と `capture-mock.ts` で作る。動きの差は仮アニメーション（`capture-mock.ts` で数秒の MP4。6 本で約 30 秒）、配置や色の差は静止画で足りる。言葉の候補（タイトル・見出し）は、実際の見出しの形に描いた静止画で 10〜15 案（4〜5 案では選び切れない）
3. **そのまま直すものも、確認画面を出す**: 「こう直します」を、直した後の見本（静止画 1 枚。`sample.ts` で本番の上で撮る）か、文言なら「直す前 → 直した後」の文（選択票の `text`）で、`mode: "view"` のページに並べ、OK をもらってから作る。言葉が 1 通りに見えても、本人の頭の中の形と違うことがある。ただし、本人が言葉で具体的に指示した直し（「かぶっている年は消していい」）で、JSON の書き換えだけで済み数分で戻せるものは、入れた版の確認画面で見せてよい
4. **まとめて本番に入れる**: 選ばれた案と確認の済んだ直しを、1 回にまとめて作り手に渡す。見本は方向の目安で、本番では作り手が質を上げる。作り手が作業中に本人から新しい直しが届いたら、それも 2 と 3 を通してから足す（作業中の作り手にそのまま流さない）
5. **できた版の直した点を見せる**: 直した点は選択票の `mode: "view"` のページで先に見せ、そのうえで次の直しを聞く

ループを回すときの決め:

- 推す案は必ず明示する（選択票の `recommend`、チャットでは理由を 1 行）
- 選んだ案にメモが付いて返ってきたら、その案のままではなく、メモの方向へ直した形を作る
- 本人が直しを並べて「どう思うか」と聞いたら、言葉ごとに賛否と理由を 1 行で返してから動く。こちらが見つけた点も「私の意見」として 3 つまで添える
- 作り手は台本に無い文（決め台詞）を足さない。事実の対応（年・件数）は作り手に渡す前に題材と突き合わせる
- 尺のように中身の量で決まる問いは、曲の長さ違いを聴き比べる BGM のページにして同じ選択票に入れる
- 作り手への指示書には、納品の最後の手順（書き出し・長さとコマ数の確認・置き場所への写し・控え・確認用の静止画・引き継ぎ書）と報告の形まで書く。書き出しで止まり、写しと控えが抜けたことがある
- 作り手が作業の途中で判断を聞いてきたら、本人が決めた線に関わるものは本人に聞き、まとめ役が置いた数字（下限の秒など）ならまとめ役が決めて、次の確認画面で本人に見せる。作業中の作り手に送った返事は届かないことがあるので、作り手から「返事待ち」と返ってきたら、決めたことを 1 通にまとめて送り直す

### ループを速く回す

往復を重くするのは書き出しではない（45 秒・60 fps でも 1〜2 分で、往復の 1〜2 割）。重いのは、膨らんだ文脈（数十万トークン）を作り手が道具を呼ぶたびに読み直す時間、見本を本番に組み直す二度手間、作り手の作業途中の止まり。下の作り（場面の並びを JSON に持つ・本番の上で見本を撮る）にしておけば、データで済む直しは作り手なしで 15 分ほど（書き出しを含む）で回る。

- **中身をデータに出す**: 方向が決まったら、文言・ロゴ・項目・拍の表・場面の時刻を 1 つの JSON（例: `content.json`）にまとめ、コードはそれを読んで描く形にしてもらう。以後の文言やロゴの直しは、まとめ役がその JSON を書き換えるだけで済み、尺や曲を変えても拍の表から全場面が付いてくる
  - 場面の並び（順と、拍で書いた長さ）も JSON に持ち、各場面の始まりは前の場面の長さを足して決める。場面の時刻を絶対の拍で持つと、場面を 1 つ足すたびに後ろの全部を手で直すことになる
  - 曲の測った値（ファイル・切り出し位置・1 拍の秒・強い一撃や終わりの部分の拍）は、手で書く中身と分けて別の JSON（例: `music.json`）に置く。曲を替えたらそのファイルだけ作り直し、拍で書いた場面の長さは付いてくる
  - この JSON は HyperFrames の標準ではない。標準の variables（`<html>` の `data-composition-variables`。`--variables-file` で差し替え、Studio で編集できる）は文字列・数値・色・真偽・選択肢の単純な値しか持てず、層や行や項目の並びは載らない。単純な値だけで済む動画なら variables を使い、並びがあるなら独自の JSON にして、共通の道具（例: `blocks.js`）が描く前に同期で読む
  - JSON を書き換えたら、書き出す前に形と参照を検査する。形は TypeScript の型を書いて `tsc` で JSON と突き合わせ、ロゴのファイルがあるか・参照する key が実在するか・時刻が前後していないかは小さなスクリプトで確かめる（JSON を TypeScript に読ませても、決まった値の一覧までは型で縛れない）
  - 共通の道具は JavaScript のままにする。HyperFrames は場面の HTML と `<script src>` をそのまま読むので、TypeScript にすると検査と書き出しの前に毎回変換が要り、変換し忘れた古いコードで書き出す事故が起きる。型で守りたいときは、JSON の形を JSON Schema で検査するか、`// @ts-check` と JSDoc で確かめる
- **雛形から始める**: `assets/scaffold/` を作業ディレクトリに写すと、上の作り（`content.json` の `scenes`・`music.json`・場面ごとの 1 ファイル・共通の部品の例・帯と見出しの重ね・型と題材ごとの検査・`HANDOFF.md` の骨組み）がそろった状態で始まる。場面の並びは `scripts/check-scenes.ts <作品>` が確かめ（長さの合計 = 尺・前後の姿勢のつながり・index.html の窓・`scenes[].limits` の下限）、題材ごとの検査は作品の `check-content.ts` に書いてそこから `checkScenes` を呼ぶ。場面の窓は `scripts/scene-windows.ts <作品> --write` が書き、Studio の時間の帯に場面の区切りが見える。曲の測った値は `beat-grid.py --music-json` が `music.json` の形で書く
- **作り手は続けて使い、膨らんだら立て直す**: 直しが続く間は同じ作り手に次の仕事を送ると、作りを読み直す時間が要らない。直しを 5 回ほど重ねたら、引き継ぎ書（例: `HANDOFF.md`。決まった見た目と動き・外された表現・ファイルの地図・データの形・拍の表・確かめ方を 200 行以内）を書かせ、新しい作り手に渡す。見た目の作りはコードに残っているので創造性は失われない。最上位のモデルに頼むのは、新しい見せ方を考える直しだけにする
- **途中の確認は軽く**: 静止画（9 枚で約 5 秒）か `--fps 30` の書き出しで確かめ、60 fps の書き出しは本人に見せるときだけにする
- **データで済む直しは、まとめ役がその場で入れる**: 文言・ロゴ・拍・場面の長さや並びのように JSON の書き換えで済む直しは、作り手を呼ばずにまとめ役が書き換え、検査を通して書き出す（数分で終わる）。作り手を呼ぶのは、新しい見た目や動きを組むときだけにする
- **作り手の確かめは、変えた所に絞る**: 型と中身の検査・HyperFrames の検査は速いので毎回回す。転換の途中を 0.25 秒刻みで撮るのは、変えた場面の前後の転換だけにする。引き継ぎ書は、作り（ファイルの分け方・データの形）が変わったときだけ書き直す
- **見た目を変えない整理は、前の版とコマを比べる**: 作りを組み直したら、前の版と 0.5 秒ごとのコマを `ffmpeg` の SSIM で比べ、同じ絵になることを確かめてから見た目の直しに進む。見た目に出にくい不具合（JSON に無いキーを読んで NaN になり、揺れが黙って消える など）も、この比べで見つかる
- **作り手に渡す前に、決めごとの食い違いを潰す**: 下限の秒・尺・拍のように互いに縛り合う数字は、指示書に書く前にまとめ役が足し算で確かめる。作業中の作り手から「この下限では収まらない」と聞かれると、返事を待つ間その作り手が止まる

## 見せ方の原則

本人の反応から分かった、紹介の動画で外れにくい形。

- **場面ごとに見出しを立てる**: 動き（積み木・年・線）だけで意味を伝えようとすると、何を伝えたいのかが伝わらない。各場面の頭に大きな見出しを出し（帯が横切る・中央に出る など、切り替わったと分かる動きで）、その後は左上に読める大きさで残す。節の切り替えは全部同じ形にそろえる。時間を詰めるために 1 か所だけ帯を通さず見出しを入れ替えると、切り替わったと気づかれない
- **1 場面で読ませるのは見出し 1 つとロゴ数個まで**: 動画の速さでは、見出し・補足 2 行・ロゴ 10 個・線を同時に出しても見出ししか読めない。詳しくはリンク先（題材）へ送る
- **冒頭はこれから流れるもののタイトルにする**: 何の動画か（「46 秒でわかる 〇〇」のように短い紹介だと分かる言い方は、流れてきた人が最後まで見る理由になる）。0 秒のコマから名前と主役が見えている形にし、数秒で過ぎない長さにする
- **題材の言葉は略さない**: 見出しは題材（リンク先）の言葉をそのまま使う。略すと「勝手に略していいのか」と迷わせ、リンク先とも食い違う
- **1 本のストーリーにする**: 項目を並べるより「積み上げてきた → 今」のように流れを持たせる。見立て（積み上げ・地層など）はストーリーの形と同じ形のものを選び、見立ての物理を守る（積み上げなら上の物を浮かせない。まとめるときは枠で切り抜かず、物そのものが縮んで形を変える）
- **見立てには中身を結ぶ**: 層や柱のような見立てだけでは、何をしてきたのかが伝わらない。見立てができた直後に、それを作った具体例（案件の一覧など）を並べ、見立ての部品から線で結ぶと、見立てと中身がつながる。一覧には詳細を出さず、番号・名前・役割・年までにして、詳細はリンク先へ送る
- **項目は 1 つずつ出す**: 全部を先に出して光らせて拾うより、1 つずつ出していく方が視線を誘導できる。1 つずつ見せた節は、最後に番号付きの一覧でそろえて見せる
- **数が増える表示は、途中の値にも意味がある物（年）だけ**: 「N つの強み」を 1 → 5 と数えると、途中で「3 つの強み」と読めてしまう。年の表示も、その数が意味を持つ場面が始まってから出す
- **ロゴは全項目そろえ、公式のカラー版を使う**: ロゴのある項目と無い項目を混ぜると高さがそろわず目立つ。ロゴの無い概念（LLM・RAG のような一般名）は一覧に出さず、ロゴの無い名前は近いもので代える（代えたロゴを残すかは本人に聞く）。素材は各社の公式のカラーロゴを集めた SVG Logos（gilbarbara/logos、CC0。Iconify の `logos`）を第一にし、無いものは theSVG（MIT。Iconify の `thesvg-color`）、それでも無いものだけ simple-icons にする。simple-icons は 1 色に塗った簡易版で、公式と形も色も違い、偽物に見える。SDK（Iconify や simple-icons の npm）を入れても届く SVG は同じなので、見え方は置き方で直す。Iconify の API は数十件続けて取ると 429 になるので、gilbarbara/logos は GitHub の raw から取る。ロゴの素材は題材のリポジトリにまとめて置くと、他の制作物でも使える
- **ロゴは枠に入れず、面積をそろえて置く**: Swift や TypeScript のように自分で四角い地を持つロゴは、枠の札に入れると二重の四角になるので、札に入れずにそのまま置く。横長・縦長のロゴ（AWS・Cloudflare の雲・v0 など）を正方形の箱に `meet` で収めると、横長のものだけ小さく潰れて見える。箱は高さだけそろえ、縦横比の平方根で幅と高さを決めて面積をそろえる（高さは正方形の 1.08 倍まで）。ロゴを出すすべての場面で同じ計算を使う
- **結び付けは線で、ほかは薄く**: 項目と根拠（例: 強みとそれを支える技術）を結ぶときは、線を 1 回伸ばし、関係のない物を薄くする。光らせる・揺らすを重ねるとうるさい
- **色には役割を持たせる**: 差し色を面いっぱいに塗ると読みにくい。薄い地にして、差し色は縁・側面・線に使う。主役の札は地と違う色にする
- **同じ情報を 2 か所に置かない**: 冒頭と締めに名前があるなら、途中に名前のブロックは要らない。同じ値が続く表示（段ごとの年が 2026・2026・2026 と続く）は、薄くして残さず、出さない
- **強調の印は 1 か所、最初に届けたいものに**: タイトルの下の行の黄の印は、見る人に最初に届けたいもの（今の肩書き）に付ける。次の場面で伝わること（年数は年の窓が回って伝わる）に付けると、同じことを 2 回言うことになる
- **締めは別のカット**: 詳細の URL を主役の札にし、題材にある外部アカウント（GitHub・X など）はロゴ付きの軽い形（丸いボタンなど）で添える。札が何か（「Web で公開中」）は、締めの面が落ちて 1 秒ほど後に札の角の吹き出しで添える
- **配分の目安**（45 秒の自己紹介）: タイトル 5 秒・見立て（積み上げ）11 秒・具体例の一覧 11 件 5 秒（行は 0.2 秒おき、出そろってから 1.5 秒読む）・技術の一覧 3.5 秒・見せ場の板 1 枚 2〜2.5 秒と最後の一覧 2 秒・締め 4〜5 秒。見せ場の板が 1 枚 3 秒、締めが 5 秒を超えると間延びする
- 既定で避けるもの: 英語の飾り文字と通し番号の札（`01 COLLECT` `FIG.01`）、本物らしく見せる作り物の数字（git のハッシュ・架空の指標）、暗い背景一色の「いかにも AI」な見た目、貼り付け型（テープ・斜めの付箋）

## 聞くこと

1 回に 1 問、推す答えを先頭にした選択肢つきで聞く。題材から読めることは聞かない。

- 動画の種類で聞き方を変える。自己紹介なら「どんな人として覚えてほしいか」。「一番伝えたいことを 1 つ」と絞らせると「全部」と答えられて進まない
- 見る人を題材のルールから決めつけず、本人の目的を聞く。要約するときは本人の言葉を返し、絞り込まない
- 雰囲気は「どう見られたいか」で聞く。「技術的なプロ感」と「派手さ」は別の軸
- 人名の読みを演出に使うときは読みを確かめる
- 書き出した動画の置き場所を、最初の書き出しの前に聞く

## 選択票（`scripts/picker.ts`）

案と BGM を 1 枚の HTML に並べ、本人が選んで「回答をまとめてコピー」を押し、会話に貼り戻す。

```bash
bun "$SKILL_DIR/scripts/picker.ts" <spec.json> <out.html>   # spec の形は --help
```

- 決めごとが複数あるときは `pages` に並べ、1 枚の中のタブで切り替える（何枚も開かせない）。タブには各ページの状態（未回答 / 回答済み / 送信済み / 送信後に変更、確認用は 未確認 / 確認済み）が出て、最後のタブ「回答のまとめ」に全ページの回答と進み具合（「まだ: …」）が集まる
- `mode: "keep"` は案を N 個まで残す（方向やキービジュアルは `keep: 1`）。`mode: "view"` はボタンなし・メモ欄だけの確認用。`mode: "pick"` は場面ごとに 1 案を選ぶ形で、本人が混ぜたいと言ったときだけ
- `images` に `.mp4` を渡すと、音なしで繰り返す動画として並ぶ（仮アニメーション用）。案に `text` を書くと、画像の代わりにその文を出す（文言・URL・尺の「直す前 → 直した後」の確認画面用）
- 案が文だけのページは、横並びにせず縦に 1 列（幅 880px まで）で並ぶ。横並びの狭いカードでは 1 行が短く折れて読みにくいため。文は改行ごとに行を分け、「1. 」で始まる行は番号つきの並び、空の行は段落の間になるので、`text` は手順なら「1. 」、話の切れ目なら空行で書く
- `recommend`（key と理由 1 行）で推す案に札「おすすめ」を付ける
- BGM は何曲でも並べられる。1 曲を再生すると他は止まり、止めた位置は残る
- 入力はブラウザに保存される。作り直したら同じ出力先に上書きし、開き直さずに「再読み込みして」と伝える

## 仮アニメーション（`scripts/capture-mock.ts`）

```bash
bun "$SKILL_DIR/scripts/capture-mock.ts" mock/H1.html mock/H2.html --out-dir mock   # → mock/H1-a.mp4 …
```

- HTML は 1920×1080 で組み、動きは CSS の `@keyframes` で書く。撮るときは全部の動きを止めて時刻を 1 コマずつ進めるので、毎回同じ絵になる
- 書体と色は本番と同じものを使い、後ろの場面は仮の形（灰色の箱など）でよい。見本だと選択票の見出しの横で断る
- 1 本 3 秒前後で、見せたい動き 1 つだけを入れる（切り替え・出方・結び方）。今の版の同じ場面を `ffmpeg -ss <秒> -t 4` で切り出して `<key>-a.mp4` として並べると、比べる基準になる

## BGM

- **公開する動画の曲は、利用条件が明記された音源から選ぶ**: 仕事につながる紹介動画は商用と読まれうる。HeyGen のカタログの曲は、規約にも API の案内にも HeyGen の外で使う条件が書かれておらず、無料プランの成果物は非商用に限られる（2026-10 時点。プランは `heygen user me get` の `subscription.plan`）。HeyGen の曲（`scripts/bgm-candidates.ts`）は試聴と方向の目安に使い、公開する版は条件が明記された音源にする
- **Mixkit が取りやすかった**: 無料ライセンス（商用可・クレジット不要、公式の案内は mixkit.co/llm-info/）。曲は `assets.mixkit.co/music/<id>/<id>.mp3`。ページを短時間に取りすぎると 429 になるので、一覧のページを中心に 15 回以内に抑える。Pixabay Music は自動の取得を Cloudflare が拒むので、探すならブラウザを操作する。曲の出どころとライセンスは作業ディレクトリの `MUSIC.md` に残す。曲の個別のページは後でサイトの検索に出なくなることがあるので、曲を決めたときに曲のページとライセンスのページを撮って控える
- **候補は多めに、テイストを散らして**: 12〜16 曲を 2 回ほど（2 回目は前と違う方向で）。4 曲では選び切れない。同じ音源で速さや和音だけを変えた見本は、どれも同じに聞こえて選べない
- **配布元の曲は動画の尺に切ってから聴き比べる**: 頭から切ってフェードアウトする版と、曲の終わりの N 秒で曲そのものの終わり方で締まる版を作り、音量（`loudnorm`）をそろえて並べる。終わりの版は、終わりの N 秒にいちばん近い小節の頭から切ると、頭が拍に乗る。冒頭が短いと言われたら、切り出しを前の小節の頭にずらして尺ごと伸ばす。動画の尺を曲より短く止めるときは、鳴り終わりの後に残る響きを音量の自動化で尺までに絞る（ぶつ切りに聞こえない）
- **拍は `scripts/beat-grid.py` で測る**: `uv run --with librosa --with numpy python -I "$SKILL_DIR/scripts/beat-grid.py" <曲> --bpm-hint 120`。1 拍の長さを拍の位置への直線の当てはめで出す。`--music-json <作品>/music.json` を付けると、1 拍の秒・尺・鳴り終わりと一番強い立ち上がりの拍を作品の `music.json` の形で書く（強い一撃や終わりの部分は聴いて直す）。librosa の tempo は解析の刻み幅に丸められ、約 121 BPM の曲が 123 BPM と出た（35 秒で約 0.6 秒ずれ、後半の動きが拍から外れる）。出た拍の表と曲の形（強い一撃・終わりの部分・鳴り終わる秒）を作り手に渡す。同じ間隔で並ぶ物（板の出る時刻など）の間隔が 4.5 拍のような半端な拍になるときは、4 拍と 5 拍の交互にして毎回拍の頭に乗せる（平均は同じ）
- ネットに出られないときの予備として、`scripts/beat-music.ts` が拍の表から BGM と効果音を合成する（既定は軽め。低音を厚くすると重く聞こえる）

## サムネと公開

0 秒のコマに任せず、別に 1 枚作る。0 秒は動きの始まりで、文字がまだそろっていない。作った 1 枚を、Web に埋め込むときの最初の絵（`<video poster>`）・README の動画の最初のコマ（下）・共有したときの絵（OGP）に使う。候補は、タイトルがそろったコマ・サムネ用に組んだ絵（写真と名前を大きく）・見せ場のコマを並べ、小さく表示されても読めるかで選んでもらう。仕上げの版から撮り直す。

- **Web に置く版**: 仕上げ（`--quality delivery`、45 秒・1080p・60 fps で約 25 MB）を `ffmpeg` の `-crf 24 -movflags +faststart` で書き直すと約 7 MB になり、見た目は変わらない。`<video controls preload="none" playsinline poster="…">` で置くと、開いただけでは読み込まず、音は再生を押したときだけ鳴る。プロフィールのような本文の前に置くときは幅を抑え（640px 前後）、PC で本文の頭が最初の画面に収まるようにする
- **共有したときの絵**: `og:image` をサムネ（1280×720）にして `twitter:card` を `summary_large_image` にすると、URL を貼ったときに大きいカードで出る
- **GitHub の README**: GitHub の画面で添付した `user-attachments` の URL を 1 行書くと、再生ボタン付きで出る（無料のアカウントは 1 本 10 MB まで。リポジトリに置いた mp4 を相対パスで書いても、再生ボタンにはならずリンクになる）。URL は Issue の作成画面の本文の欄に動画を貼ると作られ、Issue は作らずに本文を空にして閉じればよい。ブラウザを操作する道具でファイルの入力欄が画面に無いときは、一時的な `<input type=file>` を足してファイルを入れ、本文の欄に paste のイベントで渡す。その URL の行は GitHub でしか再生できないので、README から PDF や Markdown の写しを作る仕組みがあれば、そこでは外す
- **README の動画の最初の絵**: GitHub の README に埋め込んだ動画はサムネを指定できず、最初のコマが最初の絵になる。0 秒が動きの始まりで空に近い動画だと、README では何の動画か分からない。README 用には、最初の 1 コマ（1/60 秒）をサムネにして音も 1 コマ遅らせた版を書き出して添付する（`ffmpeg` の concat と `adelay`。再生中は気づかない）
- 公開する場所（Web の動画・README の添付・案内文の秒数など）は、動画を差し替えるたびに全部合わせる。使う側のリポジトリのルールに、合わせる場所の一覧を書いておく

## 書き出す前の点検

- **転換の途中を 0.25 秒ごとに見る**: 1 秒ごとの静止画では、物が飛んでくる・縮む・入れ替わる途中の重なりを見逃す。入ってくる物は自分の行・枠の中だけで動かし、他の要素の上を通さない。消える動きと現れる動きは重ねない
- **0 秒のコマが空でないか**: 無音で流れる前の絵や共有したときの絵、README に埋め込んだ動画の最初の絵になる
- **スマホの幅（390px）に縮めて読めるか**: タイムラインでは見出し・名前・URL くらいしか読めない。全画面で読めれば足りる情報と、タイムラインで読ませたい情報を分ける
- **拍に合っているか**: 曲を差し替えたり尺を変えたら、拍の表を測り直してから合わせる
- **曲の利用条件**（上の BGM の節）

## 組み立てるときの落とし穴（HyperFrames）

- 題材にない事実を足さない。動画は題材の要約で、盛ると題材そのものの信頼を落とす
- 場面ごとにサブコンポジション（`compositions/<場面>.html`）に分け、`index.html` は時刻の割り当てと音だけを持つ。ファイルの分け目は、帯のワイプのように画面を横切る切り替えに置き（1 ファイル = 切り替えから切り替えまでの 1 カット）、分け目をまたいで動きや状態を引き継がない。柱のように場面をまたいで残って見える物（この種の動画には多い）は、共通の部品として切り出す。部品は、データと姿勢（位置・大きさ・薄くした項目など）を受けて描く関数にし、場面の境目での姿勢を JSON の場面の並びに書く。各ファイルは始まりの姿勢で部品を描き直し、ワイプの境目で前後の絵が一致して続いて見える。前の場面の終わりの姿勢と次の場面の始まりの姿勢が一致しているかは、JSON の検査で確かめる。1 つの生きた物を全場面に通して受け渡す作りにすると、全場面が 1 つのファイルに集まり、場面の追加や並べ替えのたびに受け渡しが壊れる
- 共通の部品と出入りの書き方は雛形にある: 時刻・帯・出入り（`B.presence`）・時計は `assets/scaffold/assets/scenes.js`、部品の例（データと姿勢を受けて描く関数）は `assets/parts.js`、swap で入る次の場面が同じ部品を描き直すときに前の場面の部品を消すのは `B.handsOff`（同じ物を 2 枚重ねると縁が濃くなる）
- JSON から読む値が無いと計算が NaN になり、その要素の `transform` がまるごと効かなくなる（揺れと横のずれが黙って消えた）。読む値は検査で存在を確かめ、道具の側でも既定値を持つ
- 描く関数は時刻だけで決まるようにする。書き出しは並列で任意の時刻へ飛ぶので、前のコマで隠した物に頼ると、いきなり後ろの時刻を撮ったときに消し忘れが見える。場面の終わりの後に残る物は、その分岐で明示的に隠す
- 意図した重なりは、検査の印（`data-layout-allow-overlap` `data-layout-allow-occlusion`）を文字の要素そのものに付ける。祖先に付けても効かない（帯の上の文字、薄くする幕の下の字）
- 日本語の書体は HyperFrames が自動で用意しないので、`@font-face` でローカルのファイルを読むか Google Fonts の `<link>` を書く（無いと `font_family_without_font_face` で止まる）。`font-family` を書く場面ファイルごとに要り、親の宣言だけでは検査が止まる
- 和文の書体で英字の名前の横にロゴを置くときは、行の箱の中心ではなく英字の見た目の中心にそろえる。ZenMaru のような和文の書体は英字を箱の中心より下に描くので、`align-items: center` のままだとロゴが文字より上に見える。canvas の `measureText` で大文字 H と x の高さの間の中心を出し、行の箱の中心との差だけロゴを下げる
- 場面ファイルから親の DOM は読めない（検査は場面を単体でも動かす）。値はデータの JSON か `data-variable-values` で渡す
- `letter-spacing` や `width` を動かさない（フレーム撮影でかくつく）。transform と opacity で動かす
- 書き出す前に `npx hyperframes check` を通す。仕上げは `render --quality delivery`、途中は `--quality draft --fps 30`

## 置き場所

作業ディレクトリ・データの JSON・引き継ぎ書・`history.jsonl`（採った案と外した案を 1 行ずつ）は、使う側のリポジトリが決める（コミットしない場所が多い）。
