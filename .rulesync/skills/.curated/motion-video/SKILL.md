# motion-video（モーショングラフィックス動画を本人と一緒に作る）

動画は HyperFrames（HTML と GSAP で組み、ブラウザで 1 フレームずつ撮って MP4 にする）で作る。組み立て・検査・書き出しの仕組みは HyperFrames の公式スキル（`hyperframes` `hyperframes-core` `media-use` など）が持っているので、ここでは重ねない。このスキルが担うのは、本人と方向を決めて仕上げるまでの進め方と、そこで使う道具。

題材ごとの決め（事実の出どころ・本人の好み・作業場所）は、使う側のリポジトリのスキルかルールに書く。ここには、どの題材でも効く話だけを置く。

## 前提

- 使う側のリポジトリが `heygen-com/hyperframes` のスキルを `sources` で取っている（選ぶ名前と取り込みの注意は ai-rules の README「よく使う外部 source」）
- `npx hyperframes` は Node 22 以上・Chrome・ffmpeg を使う。仮アニメーションの撮影（`capture-mock.ts`）は puppeteer、拍の測定（`beat-grid.py`）は uv を使う
- 題材（事実の出どころ）・作業ディレクトリ・書き出した動画の置き場所を、使う側が決めている。決まっていなければ最初に聞く

## 進め方

1 本目は、方向が決まる前に全編を作り込んで 2 回差し戻され、雑なコマを部品ごとに選び続けた 3 回目も「こねくり回したけど微妙」と言われた。決まったのは、最上位のモデルが 1 人で作った完成に近い動画を方向違いで並べたとき。その後の仕上げは、直しのたびに仮アニメーションで方向を選んでから本番に入れる形にして、外れがなくなった。

1. **中身を文字で決める**: 場面ごとに言うこと（見出し 1 行）と、ストーリーの形（積み上がる・合流する・旅する など 1 語）を、絵を作る前に決める。中身が決まらないまま絵を選ぶと、「この数字は要らない」のような中身の不満が見た目の判断に混ざる。本人が「こういうのがいい」と思う参考（動画・画像）があれば 2〜3 本もらい、何が良いのか（密度・動き・文字・色）を言葉にする
2. **方向は完成に近い動画で選ぶ**: 最上位のモデルの作り手を 2〜3 体並列に立て、方向違いの完成に近い動画を 1 本ずつ作らせて見比べてもらう。雑なコマや静止画では「格好いいか」を判断できない。作り手への指示書には目標・中身・守る線・質の基準だけを書き、構図・動き・転換・密度は任せて大胆さを求める（場面ごとに置く要素まで決めると、誰が描いても平均的な絵になる）。方向を散らしたいときは `references/concepts.md` の棚と `scripts/draw.ts` で、互いに遠い組み合わせを引いて 1 体ずつに渡す
3. **選ばれた 1 本を、仕上げの直しのループで磨く**（次の節）

1 つの作品を場面ごとに別のエージェントに分けない（作りがそろわず、余白と主役が崩れる）。分けてよいのは、方向違いの完成品を並列で作るときと、調べ物・測定・点検。

## 仕上げの直しのループ

本人が動画を見て出す直しを、1 回ずつ次の順で回す。

1. **言葉を 2 つに分ける**: 「そのまま直すもの」（消す・足す・そろえる・色を変える）と「選んでもらうもの」（「どう見せるのがいいか」「箱でいいのか」のような見せ方の問い、言葉の候補）。読みが 1 通りの直しは聞かずにまとめて入れる
2. **読みが割れる言葉は、作る前に確かめる**: 「ボトムがしっかり」「マージンなし」のような形の言葉は、「こう読んだ」を 1 行と粗い図で見せてから作る。作り手の直し 1 回は数十万トークン（1 本目で 1 回 50〜90 万）かかり、聞くのは 1 往復で済む
3. **選んでもらうものは、仮アニメーションで見せる**: 本番を作り込む前に、まとめ役が簡単な HTML と CSS の動きで数秒の見本を 3〜4 案作り、`capture-mock.ts` で MP4 にして選択票に並べる（6 本で約 30 秒）。今の版の同じ場面も切り出して並べ、比べる基準にする。動かない差（配置・色）は静止画で足りる。言葉の候補（タイトル・見出し）は、実際の見出しの形に描いた静止画で 10〜15 案並べる（4〜5 案では「もっと」と言われた）
4. **選ばれた方向を本番に入れる**: 作り手に、選ばれた見本と「そのまま直すもの」をまとめて渡す。見本は方向の目安で、本番では作り手が質を上げる
5. **直した点を見せてから、次の直しを聞く**: 直した点は選択票の `mode: "view"` のページで先に見せる。直したことが見えないまま次を選ばせると、前の版の不満を抱えたまま選ぶ

ループを回すときの決め:

- 推す案は必ず明示する（選択票の `recommend`、チャットでは理由を 1 行）
- 選んだ案にメモが付いて返ってきたら、その案のままではなく、メモの方向へ直した形を作る
- 本人が直しを並べて「どう思うか」と聞いたら、言葉ごとに賛否と理由を 1 行で返してから動く。こちらが見つけた点も「私の意見」として 3 つまで添える
- 作り手は台本に無い文（決め台詞）を足さない。事実の対応（年・件数）は作り手に渡す前に題材と突き合わせる
- 尺のように中身の量で決まる問いは、曲の長さ違いを聴き比べる BGM のページにして同じ選択票に入れる

### ループを速く回す

1 本目では直し 1 回に 0.7〜10.6 分かかり、そのうち書き出し（36 秒の動画で約 50 秒）は 1〜2 割だった。残りは、同じ作り手を 15 回以上続けて使って膨らんだ文脈（54〜87 万トークン）を、道具を呼ぶたびに読み直す時間だった。

- **中身をデータに出す**: 方向が決まったら、文言・ロゴ・項目・拍の表・場面の時刻を 1 つの JSON（例: `content.json`）にまとめ、コードはそれを読んで描く形にしてもらう。以後の文言やロゴの直しは、まとめ役がその JSON を書き換えるだけで済み、尺や曲を変えても拍の表から全場面が付いてくる
- **作り手は文脈が膨らんだら立て直す**: 直しを 5 回ほど重ねたら、引き継ぎ書（例: `HANDOFF.md`。決まった見た目と動き・外された表現・ファイルの地図・データの形・拍の表・確かめ方を 200 行以内）を書かせ、新しい作り手に渡す。見た目の作りはコードに残っているので創造性は失われない。最上位のモデルに頼むのは、新しい見せ方を考える直しだけにする
- **途中の確認は軽く**: 静止画（9 枚で約 5 秒）か `--fps 30` の書き出しで確かめ、60 fps の書き出しは本人に見せるときだけにする

## 見せ方の原則

本人の反応から分かった、紹介の動画で外れにくい形。

- **場面ごとに見出しを立てる**: 動き（積み木・年・線）だけで意味を伝えようとすると「何を伝えたいのか分からない」と言われる。各場面の頭に大きな見出しを出し（帯が横切る・中央に出る など、切り替わったと分かる動きで）、その後は左上に読める大きさで残す
- **1 場面で読ませるのは見出し 1 つとロゴ数個まで**: 動画の速さでは、見出し・補足 2 行・ロゴ 10 個・線を同時に出しても見出ししか読めない。詳しくはリンク先（題材）へ送る
- **冒頭はこれから流れるもののタイトルにする**: 何の動画か（「46 秒でわかる 〇〇」のように短い紹介だと分かる言い方は、流れてきた人が最後まで見る理由になる）。0 秒のコマから名前と主役が見えている形にし、数秒で過ぎない長さにする
- **題材の言葉は略さない**: 見出しは題材（リンク先）の言葉をそのまま使う。略すと「勝手に略していいのか」と迷わせ、リンク先とも食い違う
- **1 本のストーリーにする**: 項目を並べるより「積み上げてきた → 今」のように流れを持たせる。見立て（積み上げ・地層など）はストーリーの形と同じ形のものを選び、見立ての物理を守る（積み上げなら上の物を浮かせない。まとめるときは枠で切り抜かず、物そのものが縮んで形を変える）
- **項目は 1 つずつ出す**: 全部を先に出して光らせて拾うより、1 つずつ出していく方が視線を誘導できる。1 つずつ見せた節は、最後に番号付きの一覧でそろえて見せる
- **数が増える表示は、途中の値にも意味がある物（年）だけ**: 「N つの強み」を 1 → 5 と数えると、途中で「3 つの強み」と読めてしまう。年の表示も、その数が意味を持つ場面が始まってから出す
- **ロゴは全項目そろえる**: ロゴのある項目と無い項目を混ぜると高さがそろわず目立つ。ロゴの無い概念（LLM・RAG のような一般名）は一覧に出さず、ロゴの無い名前は近いもので代える。ロゴの素材は題材のリポジトリにまとめて置くと、他の制作物でも使える
- **結び付けは線で、ほかは薄く**: 項目と根拠（例: 強みとそれを支える技術）を結ぶときは、線を 1 回伸ばし、関係のない物を薄くする。光らせる・揺らすを重ねるとうるさい
- **色には役割を持たせる**: 差し色を面いっぱいに塗ると読みにくい。薄い地にして、差し色は縁・側面・線に使う。主役の札は地と違う色にする
- **同じ情報を 2 か所に置かない**: 冒頭と締めに名前があるなら、途中に名前のブロックは要らない
- **締めは別のカット**: 詳細の URL を主役の札にし、題材にある外部アカウント（GitHub・X など）はロゴ付きの軽い形（丸いボタンなど）で添える
- 既定で避けるもの: 英語の飾り文字と通し番号の札（`01 COLLECT` `FIG.01`）、本物らしく見せる作り物の数字（git のハッシュ・架空の指標）、暗い背景一色の「いかにも AI」な見た目、貼り付け型（テープ・斜めの付箋）

## 聞くこと

1 回に 1 問、推す答えを先頭にした選択肢つきで聞く。題材から読めることは聞かない。

- 動画の種類で聞き方を変える。自己紹介なら「どんな人として覚えてほしいか」。「一番伝えたいことを 1 つ」と絞らせると「全部」と答えられて進まない
- 見る人を題材のルールから決めつけず、本人の目的を聞く。要約するときは本人の言葉を返し、絞り込まない
- 雰囲気は「どう見られたいか」で聞く。「技術的なプロ感」と「派手さ」は別の軸
- 人名の読みを演出に使うときは読みを確かめる
- 書き出した動画の置き場所を、最初の書き出しの前に聞く

## 選択票（`scripts/picker.ts`）

案と BGM を 1 枚の HTML に並べ、本人が選んで「回答をまとめてコピー」を押し、会話に貼り戻す。

```bash
bun "$SKILL_DIR/scripts/picker.ts" <spec.json> <out.html>   # spec の形は --help
```

- 決めごとが複数あるときは `pages` に並べ、1 枚の中のタブで切り替える（何枚も開かせない）。タブには各ページの状態（未回答 / 回答済み / 送信済み / 送信後に変更、確認用は 未確認 / 確認済み）が出て、最後のタブ「回答のまとめ」に全ページの回答と進み具合（「まだ: …」）が集まる
- `mode: "keep"` は案を N 個まで残す（方向やキービジュアルは `keep: 1`）。`mode: "view"` はボタンなし・メモ欄だけの確認用。`mode: "pick"` は場面ごとに 1 案を選ぶ形で、本人が混ぜたいと言ったときだけ
- `images` に `.mp4` を渡すと、音なしで繰り返す動画として並ぶ（仮アニメーション用）
- `recommend`（key と理由 1 行）で推す案に札「おすすめ」を付ける
- BGM は何曲でも並べられる。1 曲を再生すると他は止まり、止めた位置は残る
- 入力はブラウザに保存される。作り直したら同じ出力先に上書きし、開き直さずに「再読み込みして」と伝える

## 仮アニメーション（`scripts/capture-mock.ts`）

```bash
bun "$SKILL_DIR/scripts/capture-mock.ts" mock/H1.html mock/H2.html --out-dir mock   # → mock/H1-a.mp4 …
```

- HTML は 1920×1080 で組み、動きは CSS の `@keyframes` で書く。撮るときは全部の動きを止めて時刻を 1 コマずつ進めるので、毎回同じ絵になる
- 書体と色は本番と同じものを使い、後ろの場面は仮の形（灰色の箱など）でよい。見本だと選択票の見出しの横で断る
- 1 本 3 秒前後で、見せたい動き 1 つだけを入れる（切り替え・出方・結び方）。今の版の同じ場面を `ffmpeg -ss <秒> -t 4` で切り出して `<key>-a.mp4` として並べると、比べる基準になる

## BGM

- **公開する動画の曲は、利用条件が明記された音源から選ぶ**: 仕事につながる紹介動画は商用と読まれうる。HeyGen のカタログの曲は、規約にも API の案内にも HeyGen の外で使う条件が書かれておらず、無料プランの成果物は非商用に限られる（2026-10 時点。プランは `heygen user me get` の `subscription.plan`）。HeyGen の曲（`scripts/bgm-candidates.ts`）は試聴と方向の目安に使い、公開する版は条件が明記された音源にする
- **Mixkit が取りやすかった**: 無料ライセンス（商用可・クレジット不要、公式の案内は mixkit.co/llm-info/）。曲は `assets.mixkit.co/music/<id>/<id>.mp3`。ページを短時間に取りすぎると 429 になるので、一覧のページを中心に 15 回以内に抑える。Pixabay Music は自動の取得を Cloudflare が拒むので、探すならブラウザを操作する。曲の出どころとライセンスは作業ディレクトリの `MUSIC.md` に残す
- **候補は多めに、テイストを散らして**: 12〜16 曲を 2 回ほど（2 回目は前と違う方向で）。4 曲では選び切れなかった。同じ音源で速さや和音だけを変えた見本は、どれも同じに聞こえて選べない
- **配布元の曲は動画の尺に切ってから聴き比べる**: 頭から切ってフェードアウトする版と、曲の終わりの N 秒で曲そのものの終わり方で締まる版を作り、音量（`loudnorm`）をそろえて並べる。終わりの版は、終わりの N 秒にいちばん近い小節の頭から切ると、頭が拍に乗る。冒頭が短いと言われたら、切り出しを前の小節の頭にずらして尺ごと伸ばす
- **拍は `scripts/beat-grid.py` で測る**: `uv run --with librosa --with numpy python -I "$SKILL_DIR/scripts/beat-grid.py" <曲> --bpm-hint 120`。1 拍の長さを拍の位置への直線の当てはめで出す。librosa の tempo は解析の刻み幅に丸められ、約 121 BPM の曲が 123 BPM と出た（35 秒で約 0.6 秒ずれ、後半の動きが拍から外れる）。出た拍の表と曲の形（強い一撃・終わりの部分・鳴り終わる秒）を作り手に渡す
- ネットに出られないときの予備として、`scripts/beat-music.ts` が拍の表から BGM と効果音を合成する（既定は軽め。低音を厚くした版は「重い」と言われた）

## 書き出す前の点検

- **転換の途中を 0.25 秒ごとに見る**: 1 秒ごとの静止画では、物が飛んでくる・縮む・入れ替わる途中の重なりを見逃す。入ってくる物は自分の行・枠の中だけで動かし、他の要素の上を通さない。消える動きと現れる動きは重ねない
- **0 秒のコマが空でないか**: 無音で流れる前の絵や共有したときの絵になる
- **スマホの幅（390px）に縮めて読めるか**: タイムラインでは見出し・名前・URL くらいしか読めない。全画面で読めれば足りる情報と、タイムラインで読ませたい情報を分ける
- **拍に合っているか**: 曲を差し替えたり尺を変えたら、拍の表を測り直してから合わせる
- **曲の利用条件**（上の BGM の節）

## 組み立てるときの落とし穴（HyperFrames）

- 題材にない事実を足さない。動画は題材の要約で、盛ると題材そのものの信頼を落とす
- 場面ごとにサブコンポジション（`compositions/<場面>.html`）に分け、`index.html` は時刻の割り当てと音だけを持つ
- 場面ファイルにも `@font-face` を書く（親の宣言だけだと検査が止まる）。日本語の書体はローカルのファイルを読む
- 場面ファイルから親の DOM は読めない（検査は場面を単体でも動かす）。値はデータの JSON か `data-variable-values` で渡す
- `letter-spacing` や `width` を動かさない（フレーム撮影でかくつく）。transform と opacity で動かす
- 書き出す前に `npx hyperframes check` を通す。仕上げは `render --quality delivery`、途中は `--quality draft --fps 30`

## 置き場所

作業ディレクトリ・データの JSON・引き継ぎ書・`history.jsonl`（採った案と外した案を 1 行ずつ）は、使う側のリポジトリが決める（コミットしない場所が多い）。
