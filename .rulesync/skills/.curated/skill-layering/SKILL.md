# スキル・ルールの置き場所と書き方

スキルやルールを新しく作るとき・大きく育てたときは、書き始める前に置き場所と、ルールにするかスキルにするかを判断する。知見は上の層へ集約するほど再利用され、リポジトリに死蔵するほど腐る。

## 4 層と判断基準

| 層 | 置き場所 | 判断基準 |
|---|---|---|
| 外部由来 | 消費側 `rulesync.jsonc` の `sources` に上流リポを直接書く | 他人の配布物。改変せず参照する。本文に手を入れるなら派生として汎用層で所有する |
| 汎用 | 個人の汎用ルール集（ai-rules） | 会社名・ブランド・社内システムへの依存が本文に一切ない。他社業務でもそのまま使える |
| 会社固有 | 会社のルールリポ（例: `<org>/<org>-ai-rules`） | 会社のブランド・テーマ・製品・社内運用に依存する。ただし複数リポで使う |
| リポ固有 | そのリポの `.rulesync/skills/` / `.rulesync/rules/` | そのリポの構成・スクリプトに密結合。まずはここから始めてよい |

層が決めるのは原本の置き場所だけ。どこで読ませるか（利用範囲）は別に決める。既定は、使うリポジトリの `rulesync.jsonc` の `sources` で名前を選ぶ。選ぶのは、そのリポジトリのルール・スキルが名前で呼ぶ物（その仕事に要る物）だけにする。全セッションに載せる（グローバル）のは、マシン設定リポジトリの台帳に書いた物だけで、置く物の線は下の「何をスキル・ハーネスとして残すか」にある。

## ルールかスキルか

読まれ方が違うので、中身がいつ要るかで分ける。

- **ルール**: エージェントが自動で読む。Claude Code はルールを 1 本ずつ `.claude/rules/` に置き、`globs`（生成後は `paths`）の無い物を起動時に、ある物を合うファイルを触ったときに読む。Codex 向けは、rulesync の既定ではルートの AGENTS.md にまとめる。`agentsmd.subprojectPath` や `deriveSubprojectPathFromGlobs` を設定すると、対応するディレクトリの AGENTS.md に分けられる。これはディレクトリ階層で読む範囲を決める仕組みで、任意のファイルパターンに応じた遅延読み込みとは違う。読むプロジェクト指示の合計上限は既定 32 KiB。リポジトリの `.codex/config.toml` で上限を上げられるが、その設定は信頼済みのプロジェクトでしか読まれない
- **スキル**: スキルの段階的読み込みに対応する環境では、起動時に読むのは名前と description だけで、本文は作業が合うとモデルが判断したときに開く。開くかはモデルの判断なので、description に引き金の語を書く
- 作業を問わず効かせたい境界と、気づかずに踏む線（依存を `bun add` で足す・秘密を書く・git で履歴を消す）はルールにして短く保つ。頼まれ方で分かる作業（ルールを書く・図を作る・判断ページを出す）の判断や手順はスキルにする。長い決まりをルールに置くと、ルートにまとめて読む環境では、関係のない作業にも載る

## マクロとミクロ

仕組みを足す前に、それがどの層の話かを分ける。分けるのは責務（決める・作る）と記憶で、エージェントの数を増やすことが目的ではない。

- **マクロ**: 何を・なぜ・いつやるかを決める層。課題を立てる・優先を決める・出来を受け入れるかを判定する所で、人と、人に判断を戻す場（判断ページ・issue）、どのリポジトリでやるかの地図（ハブのリポジトリ）、定期実行がここに入る
- **ミクロ**: どう作るかをやり切る層。1 つの仕事を仕上げるためのルール・スキル・サブエージェントの分業がここに入る（下の「役割」は、ミクロの中の分け方）
- **記憶**: 会話で決まったこと・進み具合・分かったことを、会話の外に残す所（issue・記録・知識ベース・引き継ぎの文）。マクロとミクロは、会話ではなくここを介してつなぐ
- どこに足すかは、困りごとで決める
  - 作り方の知識が増えた・スキルが大きくなった → ミクロの中で分ける（役割は下の節、分ける単位は「何をスキル・ハーネスとして残すか」）
  - 何をやるか・どこまでやれば終わりかが会話ごとにぶれる → マクロの側（課題の立て方・受け入れの基準・判断を仰ぐ形）を直す。作り方のスキルを足しても、ぶれは直らない
  - 会話が終わると決めごとが消える・別の会話や別のリポジトリへ続きを渡せない → 記憶に書く形にする。うまくいかなかったことも、会話の中で直し続けず、次の課題として残す

## 役割と呼ぶ向き

層（原本の置き場所）とも、利用範囲（グローバルかリポジトリか）とも別に、スキルには呼ばれる順で決まる役割がある。スキルを足す・分けるときに 1 つ決める。

| 役割 | 持つ物 | 例 |
|---|---|---|
| 入口 | どれを使うかを選ぶ基準と、選んだ先に共通の決まり（置き場所・色の役割など） | 見せ方を選ぶ `figure`、聞き方を選ぶ `decision-page` |
| 成果物（媒体） | 1 つの成果物・1 種類の作業のやり方 | 解説動画・図解・点検のスキル |
| 素材 | 複数の成果物から使う部品 | 画像・音を作るスキル |
| 育てる道具 | スキルやルールを入れる・測る・直す | `skills-review`・`rlquiz`・`mosha-loop` |

- 他のスキルの同梱ファイル（scripts・references・assets）や節の中身に頼ってよいのは、入口 → 成果物 → 素材の向きだけにする。入口は、どの役割から頼ってもよい。素材が成果物に頼る形と、成果物どうし・素材どうしで部品を貸し借りする形は作らない。片方だけを選んだリポジトリでは頼った先が無く、エラーにもならずに機能が落ちるため。頼りたくなった部品は、下の役割のスキルへ移す。育てる道具は、どの役割のスキルも対象にしてよい
- 「〜のときは `X` スキル」と名前だけで振り分ける 1 行は、どの向きにも書いてよい
- 入口の本文に書くのは選ぶ基準までにし、選んだ先の作り方は先のスキルに置く。入口の先にもう 1 つ入口を挟まない（振り分けは 1 回）。段が増えるほど読む物が増え、どこで決まったかを追いにくくなる
- 選ぶだけで作らない役は、マクロの側にもある（中身を持たず、どのリポジトリで作業するかの地図だけを持つリポジトリ）。スキルの単位は入口、リポジトリの単位はハブと呼び分け、ほかの呼び名は増やさない。層の名前を使うのはスキルを書くときだけで、作業中のエージェントは各スキルの説明文で選ぶため
- リポジトリを束ねる単位は組織（GitHub の組織。個人のアカウントも 1 つの組織として扱う）で、ハブは組織ごとに 1 つにする。ハブが持つのは、どのリポジトリが何を担当するかの表・リポジトリをまたぐ作業・その組織で共有する基盤で、仕事の中身は持たない。地図と基盤を別のリポジトリに分けると、一緒に変わる物の行き来が増える
- いくつもの組織を触る人は、組織の上に個人の層を持つ（全部の組織のハブを並べる全体の入口・マシンの設定・配るルール集・知識ベース）。知っている向きは上から下だけにする。全体の入口はすべてのハブを知り、リポジトリは自分の組織のハブを知ってよいが、組織のハブは個人の層を指さない。ハブはその組織のほかの人も読むので、個人の物に頼らせないため。上への道は、その人のマシンのグローバルの設定に置く
- 組織が増えたら、同じ形を 1 列足す。リポジトリには組織の接頭辞を付ける。ハブは、その組織のリポジトリが 3 つを超えたら作り、全体の入口の一覧に 1 行足す。組織専用のルール集は、2 つのリポジトリで同じ決まりが要るようになったら作る（それまでは、汎用のルール集と各リポジトリのルールで足りる）
- 向きは文で頼むだけにせず、ルール集のテストで守る（スキルごとの役割の表を持ち、逆向きの参照で落とす）

## 運用ルール

- 迷ったらリポ固有から始める。ただし作ったスキルに会社名依存が無いなら、最初から汎用層に書くことを検討する
- 同じスキルを 2 つめのリポにコピーしたくなった瞬間が昇格のサイン。コピーせず、上の層へ移して両方から `rulesync.jsonc` の `sources` で参照する
- 同じ層の中で新しいスキルを立てるかは、出力形式ではなく目的と発火条件で決める。目的が同じで発火条件も重なるなら、既存スキルに型を足す（`decision-page` が案の比較モックとレビューの選択票を 1 つに持ち、`chapter-infographic` が Markdown と GitHub issue の届け先を節で分けるのがこれ）。名前を「視覚化」のような広い語にまとめると、どの場面で起動すべきかの判定が鈍る。例外は、道具の選び方そのものを持つ入口のスキル（`figure` は図の形と道具を選ぶ）で、他のスキルが名指しで呼ぶので発火の判定に頼らない。そのぶん description の発火条件は具体的な言い方に絞る
- 昇格の手順: 上の層のリポへ本文と同梱ファイルを移して push → 各リポの `rulesync.jsonc` の `skills` 選定に追加してローカルコピーを削除 → `GH_TOKEN="$(gh auth token)" bunx rulesync install --update && bunx rulesync generate`。`--update` が要る（`install` 単体は lockfile に記録済みの ref で取得するため、push したばかりのスキルはその ref に存在せず、エラーにもならず黙って取得されない。上流が動いていない状態で選定を広げるだけなら `install` でよい）
- 汎用層に置くときは会社依存箇所（ブランド名・URL・テーマ・社内用語・顧客名を含むパス）を汎用化してから移す。汎用化できない部分は会社層に分離する
- 外部由来のスキルに自分の運用の線（置き場所・寸法・使わない機能）を足したいときは、本文を書き換えず、原本を `sources` で取ったまま薄い自前スキルを重ねる（`motion-video` と HyperFrames、`figure` と draw.io の原本）。原本が `disable-model-invocation` で自分から発火しないときは、包みの description が発火を担い、本文で原本を読む形になる。原本が自分から発火する description を持ち、包みと入口が重なるときは、原本を書き換えず、使う側の設定で原本の発火を止めて包みだけを入口にする（Claude Code は `skillOverrides`、Codex は `[[skills.config]]`。一覧から外れるだけで、包みは原本のファイルを読める）。この設定は `sources` と一緒には届かないので、包みは設定が無いリポジトリでも動く形にする（自分から発火しない別の原本を選べるようにする、など）。包みを書き換える前に、その包みを取っているリポジトリを確かめる。包みは原本に無い決めだけを持ち、作り方を写さない（写すと原本が進んでも届かない）
- 外部由来のスキルはコピーせず `sources` で参照する。本文に手を入れるときだけコピーし、派生として所有する: LICENSE を同梱し、frontmatter に `source` と `forked_at`（元にした commit）を残し、本文冒頭に由来を 1 行書く（生成ツールが frontmatter のメタデータを落とすことがあるため）。派生は上流に追従しない。上流との差と上位互換は `skills-review` で点検する
- AI エージェントは、ユーザーからスキル作成を依頼されたらどの層に置くかを判断して提案すること。汎用層・会社層に置く場合は該当リポジトリでの作業になる旨を伝える

## 共有スキル・ルールを変えるとき

消費側のリポジトリで、`sources` から取り込んだスキル・ルールを直したくなったときの扱い。生成物（`.claude/skills/` `.agents/skills/` `CLAUDE.md` など）を手で直しても次の `rulesync generate` で消え、同じものを使う他のリポジトリにも届かない。直すのは上流の正本になる。上流を直すと、それを選んでいる全リポジトリに次の更新で効く。

- 直す前に、その名前を選んでいるリポジトリを `ai-rules-update` の `usage` で逆引きする。ローカルに clone していないリポジトリは数に入らないので、件数は下限として扱う
- 利用リポジトリごとに、そのスキル・ルールがどう使われているか（CLAUDE.md・AGENTS.md・`.rulesync/rules/` での参照、選んでいる他のスキルとの組み合わせ）を読み、今回の変更が効くか・邪魔になるかを 1 行ずつ書いた表をユーザーに見せる。ユーザーは上流を直すつもりがなく、目の前のリポジトリだけを直したいと思っていることが多いので、影響の広さを先に見せる
- 判定は 3 つから出す。全員に効く改善なら上流を直す。目的と発火条件が同じで出力の型だけが違うなら、同じスキルに型を足す。目的か発火条件が違うなら別のスキルに分ける（そのリポジトリだけの事情ならリポ固有層に置く）
- 承認されたら上流を直して push する。利用リポジトリへは今すぐ配らない。各リポジトリは次にそこで作業するとき、セッション開始の遅れの知らせ（`rulesync-freshness`）を見て、その場で上げるかを決める。一括で配り直す（`ai-rules-update`）のは、ユーザーが頼んだときと、利用側で壊れている不具合を直したときだけ。全リポジトリを毎回上げると、変更のたびに取得・生成・検証とコミットが利用リポジトリの数だけ走り、手間とトークンがかかる
- 外部由来のスキルは上流を直せない。手を入れるなら派生として所有するか、消費側のリポ固有スキルで補う
- 上流を読めない人（非公開の取り込み元を持たない同僚）ができることと、切り離し方は `rulesync-imports` ルール

## 書き方

今のモデルは指示への感度が高く、目的を伝えれば段取りは自分で組む。前の世代向けに書いた足場は、そのまま残すと出力を悪くすることがあり、Anthropic も OpenAI も見直しを勧めている。ただし、ある行が要らないというのは仮説で、外して比べるまで決まらない。要るかをモデルに聞いても、測ったことにはならない。

- **製品名ではなく使える機能で分ける。** 直接呼べるツール・表示先の対応形式・hook の設定状態など、選択を変える条件を書く。製品名は CLI・設定キー・固有の制約を説明するときに残す。機能が見つからないことを、別サービスの認証・課金・権限変更への許可とは扱わない
- **理由を書く。** 「X するな」だけより「Y が起きるので X しない」の方が守られ、書いていない類似ケースにも一般化される
- **強調語を使わない。** `CRITICAL` / `MUST` / 全部大文字 / 「必ず」「絶対」の連打は、感度の高いモデルでは過剰反応（頼んでいない場面での発火・過剰な検証）を生み、多用すると何も目立たなくなる。普通の文で「〜のときは〜する」と書く。どうしても 1 行だけ守られないときにその 1 行にだけ印を付ける
- **注意書きを積もらせない。** 今のモデルは「〜しない」「〜の前に確かめる」を書かれたとおりに守り、積もると関係のない場面でも確認を求めたり手を止めたりする。禁止には範囲と理由を書き、確認なしで進めてよい作業（読むだけの操作・やり直せる再実行など）は、同じ規則の中に名指しで書く。別の行に「自由に進めてよい」と足しても効かない。理由の消えた注意は、記憶・メモ・ルールから消す
- **禁止形より肯定形。** 「Markdown を使うな」より「流れる散文で書く」の方が狙った出力になる
- **ハーネスとモデルが既に持つ振る舞いを重ねない。** 「自分の仕事を検証しろ」「二重に確認しろ」「進捗を報告しろ」のような促しは、Claude Code / Codex のシステムプロンプトとモデル自身が持っている。重ねると過剰検証でトークンと時間が増えるだけで品質は上がらない。書くのは、どう確かめるか（「`bun test` で確かめる」のような、そのリポジトリの検査のコマンド）と、「どこまで検証すれば足りるか」「どの状況では止まって聞くか」といった境界の側。検査のコマンドはリポジトリごとに違い、モデルは知らないため
- **「作業前に A と B と C を全部読め」と書かない。** 「サービス境界は A、スキーマ変更は B を見る」のように、いつ何を見るかで書く。前者は毎回のツール呼び出しを増やし、後者は必要なときだけ読まれる
- **数字つきの文体の上限は、要る物だけにする。** 「N 項目まで」「N 字以内」は字面どおりに守られ、文がぶつ切りになる。読み手の事情で決めた上限だけを残し、ほかは「拾い読みできる長さに」のように狙いで書く
- **サブエージェントに回す指示には、回す場面を書く。** 回してよいのは、作っていない目が要る確かめと採点・方向の違う案を並べるとき・互いに独立で結果だけが要る調べ物の 3 つ。「毎回」と書かず、どの成果物・どの大きさのときに回すかを書く。渡すときと受け取るときに細部が落ち、仮説を渡すと仮説どおりの答えが返り、1 体ごとに費用と待ち時間がかかるため。1 つの成果物を分けて作らせること・数回の道具の呼び出しで済む確かめ・自分が文脈を持っている判断は回さない
- **矛盾を残さない。** ルール・スキル・AGENTS.md の間で指示が食い違うと、モデルは止まる・別方向へ動く・ユーザーの意図しない方の指示に従う、のどれかになる。優先順位を明示し、古い指示は消す
- **存在しないスキル・ファイルを参照しない。** 別リポ固有のスキル名やパスを汎用層の本文に残さない
- **description は短く、発火条件を具体的に。** Claude Code は description で自動起動を決め、Codex は多数導入時に description を切り詰めて表示するので、主要な用途と引き金になる語を先頭に置く。「データベースを触るとき」ではなく「マイグレーションを足す・変えるとき」。第三者視点の命令形で書く
- **同梱スクリプトは単体で使い方が分かるようにする。** `--help` で使い方を標準出力に出して終了 0、引数が合わないときは使い方を標準エラーに出して 0 以外で終える。結果は標準出力、途中経過は標準エラーに分ける（結果を JSON で返す約束のスクリプトは、エラーも JSON で返してよい）。ファイルや外部の状態を書き換える操作は、明示の引数（`--apply` など）を付けたときだけ行う。エラーは、何が起きたか・どこか（ファイルと欄）・次にどうするかまで言い切り、終了コードの意味（成功・警告・失敗・まだ途中）は 1 つのスキルの中でそろえる。呼ぶのは主にエージェントで、スタックトレースだけを返すと、直し方を推測して往復が増えるため。SKILL.md の説明とスクリプトがずれたとき、呼んだ側がその場で気づけるようにするため
- **本文は 500 行以内。** 判断材料・落とし穴・環境固有の癖を本文に置き、長い参考資料・雛形・スクリプトは `references/` `scripts/` `assets/` に分けて本文から指す（progressive disclosure）
- **常時読まれる量を意識する。** Claude Code は CLAUDE.md を 200 行目安にする（超えても切られないが、守られにくくなる）。Codex は AGENTS.md の合計を既定 32 KiB で打ち切り、ルートにまとめたルールは `globs` の有無にかかわらず読む。ディレクトリ単位に分ける場合は、その階層の AGENTS.md が読み込み対象になる。減らすのは、経緯・一覧・重複のような要らない物と、作業が限られる物のスキルへの移動までにする。信頼済みのプロジェクトで使うなら `.codex/config.toml` の上限で受け、32 KiB に収めるために境界や落とし穴は削らない
- **確実に止めたい線は指示ではなく設定に置く。** ルールは文脈であって強制ではない。Claude Code なら `permissions.deny` と `PreToolUse` hook、CI なら `needs` と検査ジョブ。指示には「なぜその線があるか」だけを残す
- **クリエイティブ系のスキル（動画・画像・スライドなど）は、固める所と任せる所を分けて書く。** 固めるのは、見る人が読み取れるかに関わる物（字幕・字の大きさの下限・色の役割など）と、毎回同じ方が慣れる物と、仕組み。任せるのは、構図・比喩・演出の強弱・言い回し。固める所は型ではなく検査で守り、任せる所には目標・中身・質の基準だけを書く。置く要素まで決めると、誰が作っても平均的な出来になる
- **書いたら外して比べる。** スキルやルールを外して同じ依頼を素のモデルに投げ、差が出ない部分は消す。文体や見せ方のように好みで良し悪しが決まる行は、モデルに採点させず、人が目隠しで読み比べる。ルールの本文を基準に渡したモデルは、ルールに沿った側を推すため。モデルが変わったら `skills-review` で測り直す

## 教訓の反映（フィードバックをスキルへ継ぎ足す）

作業中に得た教訓・ユーザーからのフィードバックは、行動が変わるべきスキル/ルールの該当セクションへ直接反映する。別ファイルの lessons メモはエージェントに読まれず腐る。

- 本文は「現在の正」を上書きする形で、決めたことと理由だけを書く。時系列ログにしない。「1 本目では」「前は〜だったが」「v18 で」「〜と言われた」のような経緯の語りも書かず、理由は今の言葉で書く（「〜すると…になるため」）。経緯は git と issue が持っている
- 日付と版の番号は書かない。書き添えるのは「日付自体に意味がある教訓」だけ（課金方針・外部仕様など、時間経過で前提が変わりうるもの）
- 反映先の層は上の 4 層判断と同じ: 汎用の教訓 → 汎用層のスキルを直して push / 会社固有 → 会社層 / そのリポだけ → そのリポの main.md かローカルスキル。汎用層・会社層を直すときは「共有スキル・ルールを変えるとき」の影響確認を通す
- 直す形は、文を足す前に仕組みで直せないかを見る。文は読まれても守られないことがあり、足すほど毎回読まれる量も増えるため
  - 決まった形で見つけられる誤り（使わない語や書式・置き場所・返答の言語の取り違え）は、検査（lint・テスト・pre-commit・CI・hook）にする。文に残すのは、検査では見分けられない判断と、その線がある理由だけ（確実に止める線の置き方は「書き方」）
  - 検査は、直せば必ず消える物だけにし、足す前に実物に当てて誤検知を数える。当たりの大半が誤検知なら入れず、文を読まないと決まらない物は別の読み手（作っていないエージェント・人）に回す。規則ごとに、落ちるべき見本を 1 つテストに持つ。通すためだけの抜け道（閾値を変える・検査の入力を書き換える・検査を外す）は、その検査を説明する所で名指しして止める。消えない警告が残ると、読むエージェントは警告ごと読み飛ばすようになるため
  - 探すのに手間取った・大きな出力を読み込んだ・要る情報に届かなかった、という詰まりは、置き場所を指す 1 行・出力を絞るスクリプト・ログや読み取り専用の権限で直す
  - hook は、ふだん何も出さない軽いスクリプトにし、条件が当たったときだけ短く出す。毎回文脈に文を足す形（UserPromptSubmit の常時注入）や、モデルを呼ぶ型（prompt・agent）は、何も起きていない回にも token を使うため
- Claude Code の auto memory はマシンローカルで、他の人にも他のマシンにも共有されない。個人の作業の癖や進行中の文脈はそこに置いてよいが、他の人や別環境でも効くべき教訓はスキル/ルールに書く
- 成果物を案で比べて選ぶスキル（台本・図・文言など）は、伏せた採点に使う物差し（評価基準）を、そのスキルの `references/rubric.md` に 1 つ持つ。作り手は読まず、採点係と直し手が読む。読み手が採点係の推しと違う案を選んだ所・ツッコんだ所から、項目を足すか説明を直す。1 本の作品だけの好みは作品の側（設定表など）に書き、次の作品でも同じ選び方をしたら rubric.md へ上げる。案を戦わせる進め方そのものは decision-page の「選ぶのを任されたとき」、人の好みとのずれを数で測るのは rlquiz、手本と比べてスキルを直すのは mosha-loop が持つので、束ねるメタのスキルは作らない
- 指摘を受けたら、まず的を射ているかで分ける。事実の誤り・壊れた手順・ルール同士の矛盾・本人が方針として言ったことは、待たずにその場で該当スキルへ入れる提案をする。その場の事情かもしれないもの、逆の場面がすぐ思いつくものは、今回は入れずに見送る。見送りまで規則にすると、規則が増えるほど今のモデルは過剰に反応する
- 入れたものも見送ったものも、スキルごとの記録 issue（そのスキルの正本があるリポに立てる。外部スキルは上流ではなく、採用を決めたルール集に立てる。題名「<スキル名> の使い心地と判断」。無ければ立てる）に 1 件 1 コメントで残す。書くのは、どんな依頼で・何を言われ・入れたか見送ったか・理由・直した commit。スキルごとの「いる・いらない」の経緯がそこからたどれ、見送ったものは `skills-review` の棚卸しで読み直して、重なっていたら入れる
- AI エージェントは「この指摘を○層の△スキルへ入れますか」と提案し、OK をもらってから直して記録 issue に書く（勝手にコミットしない）

## 何をスキル・ハーネスとして残すか

残す価値があるかは「手順を教えているか、境界を引いているか」で判断する。

- **残す: 外側のガードレール型。** モデルが自力では守れない制約や、守らせたい行動の境界を引くもの。破壊的操作の禁止、コミット規約、ブランドの確定ルール、「作る前に問い詰める」、環境固有のツールの癖（課金経路・CLI の落とし穴・特定 CLI の引数の罠）など。モデルが賢くなっても消えない
- **消す: 手順を一つずつ与える型。** 「まず A を読み、次に B を作り、C を検査する」のような段取りの指示。今のモデルは目的を伝えれば自分で段取りできるので、手順型スキルはコンテキストを食うだけになりやすい。手順の中に上の「消えない知識」が混ざっているなら、その部分だけを短く残して手順は捨てる。ただし、取り消せない操作や認証の流れのように、順番を変えると壊れる手順は 1 手ずつのまま残す。判断の要る作業と違って正しい順が 1 つしかなく、モデルに組ませると事故になるため
- **スキルを分ける単位は、頼み方・進め方・確かめ方で決める。** 見た目や出てくる物の違いでは分けない
  - 進め方が違うなら分ける（好みのテイストを探してから作る見せ場の動画と、台本を書いて声で読む解説動画など）。1 つにまとめると、どちらの頼みでも両方の手順を読むことになる
  - 設定で済む違いなら分けない（話し手の人数・キャラの有無・章・字幕など）。分けると、間の頼み（キャラなしで章に分けたい、など）をどちらで作るか迷い、共通の部品を 2 つのスキルで貸し借りすることになる
  - 複数の成果物（動画・スライド・記事）から使う部品は、素材のスキルに出す（図・生成画像・音など）。1 つの成果物でしか使わない部品は、その中に置く
  - 読ませるだけの知識（規約・判断基準）と、物を作る・書き換える手順は、大きくなったら別のスキルに分ける。混ざったままだと、知識だけ要る場面でも手順ごと読まれ、責務が濁って大きくなる。作る側のスキルが、知識の側を参照する形にする。返す物（目的）が 2 つ以上に見えるスキルは、分ける候補
  - スキルを分けたり足したりしたら、グローバルかリポジトリかは元のスキルから引き継がず、下の基準で 1 から決める。引き継ぐと、基準に当たらない物がグローバルに増える
- グローバル（全セッションで description が読まれる）に置くのは、ガードレール型と、全セッションで効くルールが名前で呼ぶスキル（とその前提）と、グローバルの入口のスキルが振り分け先として名前で呼ぶスキル（見せ方を選ぶ入口が呼ぶ動画のスキルなど）と、どのリポジトリでも使う導入と点検の道具（rulesync を入れる前に呼ぶ導入のスキル、スキルやルールを測る道具）と、どのリポジトリの作業とも関係ない個人の頼み（買い物の比較など）だけにする。ルールが呼ぶのに無いと、そのリポジトリでは雛形や決まりが効かず、入口が振り分けた先が無いと、そのリポジトリでは振り分けが行き止まりになり、導入と点検の道具はまだ sources の無いリポジトリや、どのリポジトリのルールを測るときにも要り、個人の頼みには属するリポジトリが無いため。それ以外の手順型・成果物の型（PDF 変換など）は、それを使うリポジトリの sources に入れる
- グローバルに置いた物は、リポジトリの sources に写さない。写すのは、そのリポジトリのルール・スキルが名前で呼ぶとき（リポジトリの仕事の一部になっているとき）だけ。呼ばれていない写しは、同僚のエージェントとクラウドのセッション（ユーザー単位の置き場を読まない）に、読み手個人の好みを持ち込むだけになる
