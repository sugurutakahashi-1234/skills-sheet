# スキル・ルールの置き場所と書き方

スキルやルールを新しく作るとき・大きく育てたときは、書き始める前に置き場所と、ルールにするかスキルにするかを判断する。知見は上の層へ集約するほど再利用され、リポジトリに死蔵するほど腐る。

## 4 層と判断基準

| 層 | 置き場所 | 判断基準 |
|---|---|---|
| 外部由来 | 消費側 `rulesync.jsonc` の `sources` に上流リポを直接書く | 他人の配布物。改変せず参照する。本文に手を入れるなら派生として汎用層で所有する |
| 汎用 | 個人の汎用ルール集（ai-rules） | 会社名・ブランド・社内システムへの依存が本文に一切ない。他社業務でもそのまま使える |
| 会社固有 | 会社のルールリポ（例: `<org>/<org>-ai-rules`） | 会社のブランド・テーマ・製品・社内運用に依存する。ただし複数リポで使う |
| リポ固有 | そのリポの `.rulesync/skills/` / `.rulesync/rules/` | そのリポの構成・スクリプトに密結合。まずはここから始めてよい |

層が決めるのは原本の置き場所だけ。どこで読ませるか（利用範囲）は別に決める。既定は、使うリポジトリの `rulesync.jsonc` の `sources` で名前を選ぶ。全セッションに載せる（グローバル）のは、マシン設定リポジトリの台帳に書いた物だけで、置く物の線は下の「何をスキル・ハーネスとして残すか」にある。

## ルールかスキルか

読まれ方が違うので、中身がいつ要るかで分ける。

- **ルール**: エージェントが自動で読む。Claude Code はルールを 1 本ずつ `.claude/rules/` に置き、`globs`（生成後は `paths`）の無い物を起動時に、ある物を合うファイルを触ったときに読む。Codex にはこの仕組みが無く、rulesync はルールを全部 AGENTS.md 1 本につなげ、起動時に読ませる。合計が既定 32 KiB を超えた分は黙って捨てられ、上限を上げる設定（`.codex/config.toml`）は信頼済みのプロジェクトでしか読まれない
- **スキル**: どちらのエージェントも、起動時に読むのは名前と description だけで、本文は作業が合うとモデルが判断したときに開く。開くかはモデルの判断なので、description に引き金の語を書く
- 作業を問わず効かせたい境界と、気づかずに踏む線（依存を `bun add` で足す・秘密を書く・git で履歴を消す）はルールにして短く保つ。頼まれ方で分かる作業（ルールを書く・図を作る・判断ページを出す）の判断や手順はスキルにする。長い決まりをルールに置くと、Codex では使わない作業のたびに全部読まれ、上限を超えると後ろのルールから落ちる

## 運用ルール

- 迷ったらリポ固有から始める。ただし作ったスキルに会社名依存が無いなら、最初から汎用層に書くことを検討する
- 同じスキルを 2 つめのリポにコピーしたくなった瞬間が昇格のサイン。コピーせず、上の層へ移して両方から `rulesync.jsonc` の `sources` で参照する
- 同じ層の中で新しいスキルを立てるかは、出力形式ではなく目的と発火条件で決める。目的が同じで発火条件も重なるなら、既存スキルに型を足す（`decision-page` が案の比較モックとレビューの選択票を 1 つに持ち、`chapter-infographic` が Markdown と GitHub issue の届け先を節で分けるのがこれ）。名前を「視覚化」のような広い語にまとめると、どの場面で起動すべきかの判定が鈍る。例外は、道具の選び方そのものを持つ入口のスキル（`figure` は図の形と道具を選ぶ）で、他のスキルが名指しで呼ぶので発火の判定に頼らない。そのぶん description の発火条件は具体的な言い方に絞る
- 昇格の手順: 上の層のリポへ本文と同梱ファイルを移して push → 各リポの `rulesync.jsonc` の `skills` 選定に追加してローカルコピーを削除 → `rulesync install --update && rulesync generate`。`--update` が要る（`install` 単体は lockfile に記録済みの ref で取得するため、push したばかりのスキルはその ref に存在せず、エラーにもならず黙って取得されない。上流が動いていない状態で選定を広げるだけなら `install` でよい）
- 汎用層に置くときは会社依存箇所（ブランド名・URL・テーマ・社内用語・顧客名を含むパス）を汎用化してから移す。汎用化できない部分は会社層に分離する
- 外部由来のスキルに自分の運用の線（置き場所・寸法・使わない機能）を足したいときは、本文を書き換えず、原本を `sources` で取ったまま薄い自前スキルを重ねる（`motion-video` と HyperFrames、`figure` と drawio-skill）。原本が `disable-model-invocation` で自分から発火しないときは、包みの description が発火を担い、本文で原本を読む形になる。包みは原本に無い決めだけを持ち、作り方を写さない（写すと原本が進んでも届かない）
- 外部由来のスキルはコピーせず `sources` で参照する。本文に手を入れるときだけコピーし、派生として所有する: LICENSE を同梱し、frontmatter に `source` と `forked_at`（元にした commit）を残し、本文冒頭に由来を 1 行書く（生成ツールが frontmatter のメタデータを落とすことがあるため）。派生は上流に追従しない。上流との差と上位互換は `skills-review` で点検する
- AI エージェントは、ユーザーからスキル作成を依頼されたらどの層に置くかを判断して提案すること。汎用層・会社層に置く場合は該当リポジトリでの作業になる旨を伝える

## 共有スキル・ルールを変えるとき

消費側のリポジトリで、`sources` から取り込んだスキル・ルールを直したくなったときの扱い。生成物（`.claude/skills/` `.agents/skills/` `CLAUDE.md` など）を手で直しても次の `rulesync generate` で消え、同じものを使う他のリポジトリにも届かない。直すのは上流の正本になる。上流を直すと、それを選んでいる全リポジトリに次の更新で効く。

- 直す前に、その名前を選んでいるリポジトリを `ai-rules-update` の `usage` で逆引きする。ローカルに clone していないリポジトリは数に入らないので、件数は下限として扱う
- 利用リポジトリごとに、そのスキル・ルールがどう使われているか（CLAUDE.md・AGENTS.md・`.rulesync/rules/` での参照、選んでいる他のスキルとの組み合わせ）を読み、今回の変更が効くか・邪魔になるかを 1 行ずつ書いた表をユーザーに見せる。ユーザーは上流を直すつもりがなく、目の前のリポジトリだけを直したいと思っていることが多いので、影響の広さを先に見せる
- 判定は 3 つから出す。全員に効く改善なら上流を直す。目的と発火条件が同じで出力の型だけが違うなら、同じスキルに型を足す。目的か発火条件が違うなら別のスキルに分ける（そのリポジトリだけの事情ならリポ固有層に置く）
- 承認されたら上流を直して push する。利用リポジトリへは今すぐ配らない。各リポジトリは次にそこで作業するとき、セッション開始の遅れの知らせ（`rulesync-freshness`）を見て、その場で上げるかを決める。一括で配り直す（`ai-rules-update`）のは、ユーザーが頼んだときと、利用側で壊れている不具合を直したときだけ。全リポジトリを毎回上げると、変更のたびに取得・生成・検証とコミットが利用リポジトリの数だけ走り、手間とトークンがかかる
- 外部由来のスキルは上流を直せない。手を入れるなら派生として所有するか、消費側のリポ固有スキルで補う
- 上流を読めない人（非公開の取り込み元を持たない同僚）ができることと、切り離し方は `rulesync-imports` ルール

## 書き方

今のモデルは指示への感度が高く、目的を伝えれば段取りは自分で組む。前の世代向けに書いた足場は、そのまま残すと出力を悪くすることがあり、Anthropic も OpenAI も見直しを勧めている。ただし、ある行が要らないというのは仮説で、外して比べるまで決まらない。要るかをモデルに聞いても、測ったことにはならない。

- **理由を書く。** 「X するな」だけより「Y が起きるので X しない」の方が守られ、書いていない類似ケースにも一般化される
- **強調語を使わない。** `CRITICAL` / `MUST` / 全部大文字 / 「必ず」「絶対」の連打は、感度の高いモデルでは過剰反応（頼んでいない場面での発火・過剰な検証）を生み、多用すると何も目立たなくなる。普通の文で「〜のときは〜する」と書く。どうしても 1 行だけ守られないときにその 1 行にだけ印を付ける
- **禁止形より肯定形。** 「Markdown を使うな」より「流れる散文で書く」の方が狙った出力になる
- **ハーネスとモデルが既に持つ振る舞いを重ねない。** 「自分の仕事を検証しろ」「二重に確認しろ」「進捗を報告しろ」のような促しは、Claude Code / Codex のシステムプロンプトとモデル自身が持っている。重ねると過剰検証でトークンと時間が増えるだけで品質は上がらない。書くのは、どう確かめるか（「`bun test` で確かめる」のような、そのリポジトリの検査のコマンド）と、「どこまで検証すれば足りるか」「どの状況では止まって聞くか」といった境界の側。検査のコマンドはリポジトリごとに違い、モデルは知らないため
- **「作業前に A と B と C を全部読め」と書かない。** 「サービス境界は A、スキーマ変更は B を見る」のように、いつ何を見るかで書く。前者は毎回のツール呼び出しを増やし、後者は必要なときだけ読まれる
- **矛盾を残さない。** ルール・スキル・AGENTS.md の間で指示が食い違うと、モデルは止まる・別方向へ動く・ユーザーの意図しない方の指示に従う、のどれかになる。優先順位を明示し、古い指示は消す
- **存在しないスキル・ファイルを参照しない。** 別リポ固有のスキル名やパスを汎用層の本文に残さない
- **description は短く、発火条件を具体的に。** Claude Code は description で自動起動を決め、Codex は多数導入時に description を切り詰めて表示するので、主要な用途と引き金になる語を先頭に置く。「データベースを触るとき」ではなく「マイグレーションを足す・変えるとき」。第三者視点の命令形で書く
- **同梱スクリプトは単体で使い方が分かるようにする。** `--help` で使い方を標準出力に出して終了 0、引数が合わないときは使い方を標準エラーに出して 0 以外で終える。結果は標準出力、途中経過は標準エラーに分ける（結果を JSON で返す約束のスクリプトは、エラーも JSON で返してよい）。ファイルや外部の状態を書き換える操作は、明示の引数（`--apply` など）を付けたときだけ行う。SKILL.md の説明とスクリプトがずれたとき、呼んだ側がその場で気づけるようにするため
- **本文は 500 行以内。** 判断材料・落とし穴・環境固有の癖を本文に置き、長い参考資料・雛形・スクリプトは `references/` `scripts/` `assets/` に分けて本文から指す（progressive disclosure）
- **常時読まれる量を意識する。** Claude Code は CLAUDE.md を 200 行目安、Codex は AGENTS.md の合計を既定 32 KiB で打ち切る。Codex では `globs` を書いたルールも起動時に読まれるので、量を減らすには、短くするか、作業が限られる物をスキルに移す（上の「ルールかスキルか」）
- **確実に止めたい線は指示ではなく設定に置く。** ルールは文脈であって強制ではない。Claude Code なら `permissions.deny` と `PreToolUse` hook、CI なら `needs` と検査ジョブ。指示には「なぜその線があるか」だけを残す
- **書いたら外して比べる。** スキルやルールを外して同じ依頼を素のモデルに投げ、差が出ない部分は消す。文体や見せ方のように好みで良し悪しが決まる行は、モデルに採点させず、人が目隠しで読み比べる。ルールの本文を基準に渡したモデルは、ルールに沿った側を推すため。モデルが変わったら `skills-review` で測り直す

## 教訓の反映（フィードバックをスキルへ継ぎ足す）

作業中に得た教訓・ユーザーからのフィードバックは、行動が変わるべきスキル/ルールの該当セクションへ直接反映する。別ファイルの lessons メモはエージェントに読まれず腐る。

- 本文は「現在の正」を上書きする形で、決めたことと理由だけを書く。時系列ログにしない。「1 本目では」「前は〜だったが」「v18 で」「〜と言われた」のような経緯の語りも書かず、理由は今の言葉で書く（「〜すると…になるため」）。経緯は git と issue が持っている
- 日付と版の番号は書かない。書き添えるのは「日付自体に意味がある教訓」だけ（課金方針・外部仕様など、時間経過で前提が変わりうるもの）
- 反映先の層は上の 4 層判断と同じ: 汎用の教訓 → 汎用層のスキルを直して push / 会社固有 → 会社層 / そのリポだけ → そのリポの main.md かローカルスキル。汎用層・会社層を直すときは「共有スキル・ルールを変えるとき」の影響確認を通す
- Claude Code の auto memory はマシンローカルで、他の人にも他のマシンにも共有されない。個人の作業の癖や進行中の文脈はそこに置いてよいが、他の人や別環境でも効くべき教訓はスキル/ルールに書く
- 指摘を受けたら、まず的を射ているかで分ける。事実の誤り・壊れた手順・ルール同士の矛盾・本人が方針として言ったことは、待たずにその場で該当スキルへ入れる提案をする。その場の事情かもしれないもの、逆の場面がすぐ思いつくものは、今回は入れずに見送る。見送りまで規則にすると、規則が増えるほど今のモデルは過剰に反応する
- 入れたものも見送ったものも、スキルごとの記録 issue（そのスキルの正本があるリポに立てる。外部スキルは上流ではなく、採用を決めたルール集に立てる。題名「<スキル名> の使い心地と判断」。無ければ立てる）に 1 件 1 コメントで残す。書くのは、どんな依頼で・何を言われ・入れたか見送ったか・理由・直した commit。スキルごとの「いる・いらない」の経緯がそこからたどれ、見送ったものは `skills-review` の棚卸しで読み直して、重なっていたら入れる
- AI エージェントは「この指摘を○層の△スキルへ入れますか」と提案し、OK をもらってから直して記録 issue に書く（勝手にコミットしない）

## 何をスキル・ハーネスとして残すか

残す価値があるかは「手順を教えているか、境界を引いているか」で判断する。

- **残す: 外側のガードレール型。** モデルが自力では守れない制約や、守らせたい行動の境界を引くもの。破壊的操作の禁止、コミット規約、ブランドの確定ルール、「作る前に問い詰める」（grill-me 系）、環境固有のツールの癖（課金経路・CLI の落とし穴・特定 CLI の引数の罠）など。モデルが賢くなっても消えない
- **消す: 手順を一つずつ与える型。** 「まず A を読み、次に B を作り、C を検査する」のような段取りの指示。今のモデルは目的を伝えれば自分で段取りできるので、手順型スキルはコンテキストを食うだけになりやすい。手順の中に上の「消えない知識」が混ざっているなら、その部分だけを短く残して手順は捨てる。ただし、取り消せない操作や認証の流れのように、順番を変えると壊れる手順は 1 手ずつのまま残す。判断の要る作業と違って正しい順が 1 つしかなく、モデルに組ませると事故になるため
- グローバル（全セッションで description が読まれる）に置くのは、ガードレール型と、全セッションで効くルールが名前で呼ぶスキル（とその前提）と、どのリポジトリでも使う導入と点検の道具（rulesync を入れる前に呼ぶ導入のスキル、スキルやルールを測る道具）だけにする。ルールが呼ぶのに無いと、そのリポジトリでは雛形や決まりが効かず、導入と点検の道具はまだ sources の無いリポジトリや、どのリポジトリのルールを測るときにも要るため。それ以外の手順型・成果物の型（PDF 変換など）は、それを使うリポジトリの sources に入れる
